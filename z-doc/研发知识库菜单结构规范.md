# 研发知识库菜单结构规范

> 本文档记录 `docs/dev-knowledge/` 研发知识库侧边栏的**统一分组模型**与**维护约定**，供 AI 助手和开发者在新增/调整菜单时保持一致。
> **状态：已实施 ✅**（2026-10 完成 8 个体系的全量重构，288 篇文档链接与全部 nanoid id 零丢失）
> 侧边栏配置位置：`docs/.vitepress/config/sidebar/dev-knowledge/`（薄装配器 `dev-knowledge.js` + 每体系一个子文件）

---

## 一、核心约束（改菜单的铁律）

调整菜单时**只动菜单结构，绝不动源文件**：

1. **`link` 路径逐字不变** —— 菜单分组/层级可以随意重排，但每个叶子项的 `link` 必须指向文档真实位置，不得因分组调整而修改。
2. **`id` 永久保留** —— 每个带 `link` 的叶子项必须含 24 位 nanoid `id`，作为抗遗忘复习系统的稳定锚点。id 一旦生成永不修改，即使 `text`/`link` 变更也保持原值。
3. **源文件位置不动** —— 菜单层级与文件目录层级**解耦**，重排菜单不需要移动 `.md` 文件。

> 校验方式：改完后用 `git show HEAD:<file> | grep "link:"` 与当前文件比对，链接集合必须完全一致（新增文档除外）。

## 二、跨框架统一顶级结构模型

Vue / React / Flutter 等**框架体系**统一采用以下顶级分组顺序与命名：

```
<X> 体系
├── 架构设计        ← 领域分组（状态/路由/网络/渲染性能/工程结构 等）
├── 思考文档        ← 对应 thinking/ 目录（原「研发思维」，已统一命名并提升为顶级）
├── 底层原理拆解    ← 对应 typical-analysis/ 目录（原「典型拆解/架构设计·典型拆解」）
├── 技术选型        ← 对应 technology-selection/ 目录（顶级，不再嵌在架构设计内）
└── 面试知识库      ← 按 初级[P4-P5] / 中级[P5-P6] / 高级[P6-P7/P8] 分级
```

设计意图：

- **降嵌套深度**：思考文档/底层原理拆解提升为顶级后，叶子最深仅 3 层（体系 → 分组 → 叶子），避免 VitePress 侧边栏过度缩进。
- **跨体系一致**：用户在任意框架间跳转都是同一套心智模型。

### 命名统一对照（历史别名 → 规范名）

| 历史别名（已废弃）                          | 统一规范名       | 对应源目录          |
| ------------------------------------------- | ---------------- | ------------------- |
| 典型拆解 / 架构设计·典型拆解 / 底层原理拆解 | **底层原理拆解** | `typical-analysis/` |
| 研发思维 / 思考文档 / 跨框架研发思维        | **思考文档**     | `thinking/`         |
| 性能思考                                    | **性能优化**     | `performance/`      |

## 三、超长扁平列表的二级拆分原则

单个分组超过约 12 项时，应按**主题**或**难度标签（P 级）**拆出二级子分组：

| 体系     | 原扁平分组               | 拆分后二级子分组                                        |
| -------- | ------------------------ | ------------------------------------------------------- |
| Flutter  | 思考文档（22）           | 平台与原生 / 渲染与状态原理 / 数据与网络 / 工程化与安全 |
| Flutter  | 架构设计（10 散叶子）    | 状态与路由 / 网络层 / 渲染与性能 / 工程结构             |
| 跨域知识 | 通用基础（33）           | 核心概念 / 入门基础 [P4-P5] / 进阶实战 [P5-P6]          |
| 跨域知识 | 工程化实践（16）         | 架构解析 / 工程化面试                                   |
| 跨域知识 | 架构愿景与系统设计（17） | 架构愿景 / 前端架构 [P8] / 系统设计 [P8]                |

**反模式**：不要为单个文档硬造「一条目的分组」。单篇文档保留为叶子即可（如 Vue 架构设计下的 `Composable 设计模式`、`性能优化系统手册`）。

## 四、非框架体系的特殊约定

- **学习路径导航**：分「职级进阶」（初级 P4-P5 → 中级 → 高级 → 架构师 P8 → 技术主管 TL）与「框架专题」（如 Flutter 学习路径）两组。
- **JS / TS 体系**：无独立「架构设计/技术选型」，顶级仅「底层原理拆解」+「面试知识库」；面试库按 初级/中级/JavaScript 深度/TypeScript 高阶 分组。
- **Node.js / Python 体系**：即使技术选型只有 1 篇，仍提为顶级「技术选型」组，以保持跨体系一致（此为判断性决策，若嫌稀疏可回退嵌入架构设计）。
- **跨域知识**：非框架绑定，按知识域分组（通用基础/数据结构/设计模式/浏览器与网络/工程化实践/架构愿景与系统设计/跨框架思考文档/框架对比与选型/AI 与新技术/API 与跨平台/技术管理）。

## 五、新增/修改菜单的标准流程

```
1. 定位对应体系子文件：docs/.vitepress/config/sidebar/dev-knowledge/<framework>.js
   （改装配器以外的子文件，不要改 dev-knowledge.js 装配器）
2. 按本规范的顶级模型与命名，把新叶子放进正确的分组
3. 新叶子先不写 id，运行：node scripts/inject-sidebar-ids.mjs 自动生成 id
4. 运行：pnpm gen:doc-list 同步 doc-list.json（菜单层级变更需同步）
5. 校验：git diff 比对 link 集合无意外变更、无重复 id、无缺 id 叶子
```
