# 企业级项目 AI 指令集分层体系（讨论稿）

## 一、背景与目标

在实际企业级多人协作项目中（Vue、React、Flutter、全栈等），AI 辅助开发需要从"随手问"升级到"工程化"。  
通过建立分层的 AI 指令集体系，实现：

- AI 输出质量更稳定、更可预期
- 多人团队使用 AI 时标准统一
- 长周期项目时隔一段时间后仍可快速恢复知识脉络
- 几十万行乃至百万行代码的大项目也能有效覆盖

---

## 二、指令集分层定义

### 第 0 层：项目健康度巡检（定期执行）

> 定期执行（如每周/每个迭代），偏运维治理

- 依赖版本检查、废弃 API 使用扫描、测试覆盖率趋势
- 输出**与上次报告的对比报告**，量化变化
- 执行结果记录时间和报告位置，可追溯

### 第 1 层：基础提示词（固定前置）

> 适配当前项目的约束性文件，作为 AI 的固定阅读前置知识

- 技术栈声明、目录结构约定、命名规范
- 核心架构模式说明（如装配模式、模块化规范）
- 团队约定的"红线"（禁止事项）
- 模块索引文件：让 AI 知道"去哪找什么"，避免盲目搜索

**落地要点：**

- 可直接作为新成员入职的"项目认知手册"
- 需要明确指定作用域（哪些文件/目录）

### 第 2 层：日常开发模块级别（高频使用）

> 贴合架构的日常开发、迭代、修复、模块自检

- 按模块/功能域拆分，每个指令独立可执行
- 支持参数化（指定模块路径、组件名等）
- 输入输出明确，预期耗时清晰

**落地要点：**

- 不要一个大文件涵盖所有，保持"轻而准"
- 每个指令附带前置条件说明，降低使用门槛

### 第 3 层：项目级代码检查（插件 + AI 互补）

> 插件做前置，AI 聚焦插件无法分析的维度

- ESLint / Prettier 等能做的，不写进指令集
- AI 聚焦：业务逻辑一致性、跨模块依赖合理性、命名语义准确性
- 适合当前项目的规范性检查

### 第 4 层：版本上线前核心功能检查

> 核心功能不能出错

- 维护一份**核心功能清单**（而非每次临时列）
- 可与 CI/CD 流水线联动
- 输出检查报告

### 第 5 层：文档生成

> 业务线文档、架构文档、流程图、注释代码文档

- 区分"给人看的"和"给 AI 后续消费的结构化文档"
- 流程图需限定输入格式，保证生成质量稳定
- 符合特定模式规范的注释 → 自动生成文档

## 三、通用要求（适用于所有层的执行规范）

> 每层指令在每次执行时都必须遵守的运营层面要求

### 3.1 文档与记录

| 要求       | 说明                                    |
| ---------- | --------------------------------------- |
| 执行记录   | 每次执行需记录时间和报告输出位置        |
| 版本对比   | 大部分文档需要输出与上次报告版本的对比  |
| 更新日志   | 指令集本身需要维护更新日志（Changelog） |
| 伴生文档站 | 使用 VitePress 建立伴生文档站，统一查阅 |

### 3.2 指令集格式

| 要求      | 说明                                                                              |
| --------- | --------------------------------------------------------------------------------- |
| 人阅读版  | Markdown 文档，有说明、有示例、有上下文                                           |
| AI 阅读版 | 结构化格式（JSON/YAML 或带明确标记的 Markdown），去掉解释性文字，只保留约束和规则 |
| 参数管道  | 部分指令为固定型，部分需要参数管道分流（输入 → 处理 → 输出）                      |

### 3.3 维护与迭代

| 要求       | 说明                                                            |
| ---------- | --------------------------------------------------------------- |
| 入口文件   | 每种指令集需要各自的入口文件，方便调用                          |
| 维护指引   | 为适配不同项目，需增加各分组的指令新增/维护指引                 |
| 版本管理   | 指令集跟代码一样走 Git 管理，每次修改有 commit 记录             |
| 独立目录   | 指令集放在独立目录（如 `ai-instructions/`），与代码解耦但同仓库 |
| 维护责任人 | 每层指令指定维护责任人，防止指令集腐化                          |

## 四、设计要求（指令集体系的设计原则）

> 设计和构建指令集体系时应遵循的工程原则，不是每次执行都要跑一遍，而是确保指令集本身的设计质量

### 4.1 专业术语映射

每个指令集应配套术语映射文件，统一 AI 与团队对同一概念的理解：

| 设计要求     | 说明                                                                         |
| ------------ | ---------------------------------------------------------------------------- |
| 术语映射文件 | 维护一份项目专属的术语表（glossary）                                         |
| 映射内容     | 包含：业务术语 ↔ 代码命名、架构概念 ↔ 实际目录/文件、缩写/俗称 ↔ 正式名称    |
| 双版本维护   | 人阅读版：带解释和示例的术语表；AI 阅读版：键值对映射，用于消歧和上下文对齐  |
| 强制引用     | 指令集中涉及专业术语时，必须引用术语映射文件，避免 AI 因术语歧义产生错误理解 |

### 4.2 指令门禁（Gate Check）

> 设计原则：每条指令必须定义执行前的准入条件，不满足则拒绝执行

- **前置条件校验**：定义必要输入参数清单，检查上下文是否完整
- **环境检查**：确认当前项目状态是否允许执行（如分支是否正确、依赖是否安装）
- **权限检查**：确认当前操作是否在指令集授权范围内
- **存疑即问**：信息不完整或存在歧义时，必须主动提问确认，禁止自行猜测

### 4.3 规范（Specification）

> 设计原则：每条指令必须定义执行过程中应遵守的行为规范

- **单次执行约束**：一条指令只承担一类任务，禁止混合多种任务类型
- **输出格式规范**：每类指令的输出必须符合预定义的格式模板
- **命名规范**：生成的文件、函数、变量必须遵循项目命名约定
- **引用规范**：修改代码时必须引用对应的架构参照文件，确保一致性

### 4.4 约束（Constraint）

> 设计原则：每条指令必须声明不可违反的硬性限制

- **作用域约束**：每层指令只能操作其定义范围内的文件/目录
- **依赖约束**：不得引入项目未声明的依赖，不得升级未经评审的依赖版本
- **架构约束**：不得违反项目既定的架构分层规则（如跨层调用、循环依赖）
- **安全约束**：不得修改配置文件中的敏感信息（密钥、证书等）

### 4.5 熔断（Circuit Breaker）

> 设计原则：每条指令必须内置异常停止机制，防止错误扩散

- **范围熔断**：任务不在指令集有效范围内时，立即停止并说明原因及需完善的内容
- **卡点熔断**：执行过程中遇到无法解决的问题时，主动停止并列出卡点清单
- **置信度熔断**：当 AI 对输出结果的置信度低于阈值时，标记为"需人工确认"而非强行输出
- **递归熔断**：当检测到循环依赖或无限递归风险时，立即中断并报告
- **禁止行为**：禁止强行编造、禁止跳过问题、禁止静默失败

### 4.6 边界（Boundary）

> 设计原则：每条指令必须明确声明"能做什么"和"不能做什么"

- **验证边界**：默认只做静态分析，不主动启动项目运行验证；仅当明确配置或要求时才执行
- **分析边界**：明确区分"可自动修复"和"仅报告建议"的操作类型
- **认知边界**：AI 应明确声明哪些结论是基于代码分析的、哪些是基于推测的
- **操作边界**：定义哪些操作需要人工确认后才能执行（如删除文件、修改公共配置）

### 4.7 控制机制设计总结

| 机制 | 触发时机       | 核心目的             | 设计产出                      |
| ---- | -------------- | -------------------- | ----------------------------- |
| 门禁 | 执行前         | 确保条件具备才执行   | 前置条件清单、环境检查项      |
| 规范 | 执行中（软性） | 保证输出质量和一致性 | 格式模板、命名规则、引用规则  |
| 约束 | 执行中（硬性） | 防止越界操作         | 作用域白名单、禁止操作清单    |
| 熔断 | 异常时         | 防止错误扩散         | 停止条件、卡点上报格式        |
| 边界 | 全程           | 明确能力范围         | 能做/不能做清单、确认触发条件 |

## 五、大项目特殊考量

针对几十万行、百万行代码的项目：

1. **模块索引优先**：每层指令需明确作用域，通过模块索引文件引导 AI 定位，而非全量扫描
2. **指令拆分粒度**：大模块需进一步拆分为子指令，单次指令覆盖范围可控
3. **结果可追溯**：所有执行结果持久化存储，支持历史回溯和趋势分析
4. **增量执行**：支持只处理变更部分（结合 Git diff），避免重复全量检查

---

## 六、单人项目的价值

即便是单人维护的项目，成套指令集同样有价值：

- 较长时间后再次维护时，快速恢复项目知识脉络
- 基础提示词 = 项目记忆，不会遗忘
- 核心功能检查清单 = 上线前的安全网
- 文档生成 = 降低"只有自己能看懂"的风险

> 设计原则：共享资源集中管理，各层独立可执行，执行产物与指令分离


**结构设计说明：**

| 设计决策                           | 理由                                   |
| ---------------------------------- | -------------------------------------- |
| `shared/` 集中管理术语、约束、规范 | 避免各层重复定义，修改一处全局生效     |
| 每层独立目录 + `entry.md` 入口     | 各层可独立调用，互不干扰               |
| `entry.md` 作为每层唯一入口        | 统一调用入口，内部路由到具体子指令     |
| `reports/` 独立于指令目录          | 执行产物与指令定义分离，便于清理和归档 |
| `guides/` 独立维护指引             | 降低协作门槛，新成员知道怎么扩展       |
| `layer-N-` 前缀命名                | 层级关系一目了然，排序自然             |
| 术语表双版本（`.md` + `.ai.yaml`） | 同一信息源，两种消费方式               |

**与现有 `docs/instructions/` 体系的关系：**

- 本结构是**通用模板**，适用于任何项目
- 实际部署时，可放入 `docs/instructions/<框架>/<指令集名>/` 下，复用两级隔离
- `shared/` 中的约束和规范可被现有 `vue-assembler` 等指令集引用
- 伴生文档站通过 VitePress 直接渲染 `README.md` 和各层文档

### 7.2 参数管道设计（建议方案）

> 核心原则：不强制统一格式，按指令集实际需求设计；无参数的指令直接执行，零记忆负担

#### 7.2.1 两种执行模式

| 模式       | 适用场景                     | 调用方式                     | 示例                                                             |
| ---------- | ---------------------------- | ---------------------------- | ---------------------------------------------------------------- |
| 直接执行   | 流程固定、无需外部输入       | 从 `entry.md` 选中指令直接跑 | 基础提示词加载、健康度巡检、上线前检查                           |
| 参数化执行 | 需要指定作用域、类型、范围等 | 提供参数后执行               | 日常开发（指定模块）、代码检查（指定文件）、文档生成（指定类型） |

#### 7.2.2 各层参数需求分析

| 层级               | 参数需求     | 说明                                             |
| ------------------ | ------------ | ------------------------------------------------ |
| 第 0 层 健康度巡检 | 可选参数     | 默认全量巡检，可指定模块范围                     |
| 第 1 层 基础提示词 | **无参数**   | 固定流程，直接加载全部上下文                     |
| 第 2 层 日常开发   | **必须参数** | 模块路径、组件名、任务类型等，每条子指令参数不同 |
| 第 3 层 代码检查   | 可选参数     | 默认全项目检查，可指定文件/目录范围              |
| 第 4 层 上线检查   | **无参数**   | 固定流程，按核心功能清单逐项检查                 |
| 第 5 层 文档生成   | **必须参数** | 文档类型、作用域、输出位置                       |

#### 7.2.3 参数声明规范

每条指令在其文件顶部声明参数，格式统一：

```markdown
<!--
@instruction: 新功能开发
@mode: parameterized
@params:
  - name: module
    type: string
    required: true
    description: 目标模块路径
    example: project/code-tool-app/pages/excel-stats
  - name: component
    type: string
    required: false
    description: 目标组件名（不指定则操作整个模块）
-->
```

无参数指令同样声明，明确标注：

```markdown
<!--
@instruction: 基础提示词加载
@mode: fixed
@params: none
-->
```

#### 7.2.4 参数传递方式

不同指令集可根据自身场景选择合适的方式，不强制统一：

| 方式         | 适用场景                   | 示例                                |
| ------------ | -------------------------- | ----------------------------------- |
| 行内参数     | 参数少（1-2 个），简单直接 | `执行 fix 指令，module=pages/login` |
| 参数块       | 参数多（3+ 个），结构清晰  | 在指令调用时附带 YAML 参数块        |
| 配置文件引用 | 参数可复用、需持久化       | 指令读取 `config.md` 中的预配置     |

#### 7.2.5 参数校验规则

| 校验项   | 说明                                                    |
| -------- | ------------------------------------------------------- |
| 必填检查 | `required: true` 的参数未提供时，触发门禁拦截，提示补充 |
| 类型检查 | 参数值必须符合声明的 type（string / path / enum）       |
| 范围检查 | path 类型参数必须指向实际存在的目录/文件                |
| 存疑即问 | 参数值有歧义时，不猜测，主动询问确认                    |

#### 7.2.6 设计决策说明

| 决策                              | 理由                                                       |
| --------------------------------- | ---------------------------------------------------------- |
| 不强制跨指令集统一参数格式        | 不同层、不同指令集的参数场景差异大，强制统一反而增加复杂度 |
| 参数声明放在指令文件顶部          | 声明即文档，AI 读取指令文件时自动获取参数定义              |
| 无参数指令明确标注 `@mode: fixed` | 入口文件可直接列出所有“一键执行”的指令，降低使用门槛       |
| 参数传递方式可选                  | 行内、参数块、配置文件三种方式按场景选择，实用为主         |
| 校验失败触发门禁                  | 与第四章 4.2 指令门禁机制联动，参数不齐不执行              |

### 7.3 伴生文档站的栏目结构设计（建议方案）

> 核心思路：代码注解驱动文档自动生成，文档结构以实际项目代码为准，而非手动维护

#### 7.3.1 整体流程

```
代码中的注解标记 → 脚本扫描抓取 → 解析编排 → 生成树形文档目录 → VitePress 渲染
```

不是手动写文档目录，而是通过脚本从代码中提取注解，按算法自动生成文档树。

#### 7.3.2 注解标记格式

在代码中嵌入结构化注解，脚本通过匹配 `AUTO_DOC_` 关键字抓取。

**层级关系：**

```
UUID ←→ TITLE          一对一，一个 UUID 只对应一个 TITLE
UUID → SECTION (N)     一对多，一个 UUID 可包含多个 SECTION
SECTION → CONTENT (N)  一对多，每个 SECTION 可包含一个或多个 CONTENT
```

**实际代码示例：**

```javascript
/**
 * AUTO_DOC_UUID: 83232893Y28Y8Y2930U302U
 * AUTO_DOC_TITLE: 通用代码
 * AUTO_DOC_SECTION: 通用代码示例
 * AUTO_DOC_CONTENT:
 * 这是示例的通用代码
 *
 * AUTO_DOC_SECTION: 使用场景
 * AUTO_DOC_CONTENT:
 * 用于判断当前运行平台是桌面端还是移动端
 *
 * AUTO_DOC_SECTION: 注意事项
 * AUTO_DOC_CONTENT:
 * 需要在 Quasar 环境下使用
 * 通过 $q.platform.is 访问
 */
const isDesktop = $q.platform.is.desktop
const isMobile = $q.platform.is.mobile
```

**字段说明：**

| 字段               | 关系 | 说明                                                                                                |
| ------------------ | ---- | --------------------------------------------------------------------------------------------------- |
| `AUTO_DOC_UUID`    | 1:1  | 文档节点唯一标识，全局不重复，**可跨文件**                                                          |
| `AUTO_DOC_TITLE`   | 1:1  | 文档节点标题，与 UUID 一一对应，**用 `/` 切割生成目录层级**（如 `架构/脚手架/设计思路` → 三层目录） |
| `AUTO_DOC_SECTION` | 1:N  | 段落标题，同一 UUID 下可有多个不同 SECTION，**按 SECTION 值自然排序**（如 1.概述 2.用法）           |
| `AUTO_DOC_CONTENT` | 1:N  | 段落内容，**Markdown 语法**，可直接拼接生成文档，每个 SECTION 下可跟多行 CONTENT                    |

**脚本解析规则：**

```
遇到 AUTO_DOC_UUID → 创建新文档节点（或合并到已有 UUID）
遇到 AUTO_DOC_TITLE → 绑定标题，按 `/` 切割生成目录路径
遇到 AUTO_DOC_SECTION → 在当前 UUID 下创建新段落
遇到 AUTO_DOC_CONTENT → 追加到当前 SECTION 的内容（Markdown 语法，直接拼接）
每次记录注解时同时记录来源文件路径和行号

排序规则：同一 UUID 内的多个 SECTION 按 SECTION 值自然排序
例如："1.概述" < "2.用法" < "3.API" < "10.更新日志"

目录生成规则：TITLE 按 `/` 切割，每段对应一层目录
例如："架构/脚手架/设计思路" → docs/架构/脚手架/设计思路.md
```

#### 7.3.3 脚本处理流程

```
1. 全局扫描：遍历指定目录下所有文件，匹配 AUTO_DOC_ 关键字
   ⚠️ 跨文件抓取：同一 UUID 可能出现在多个文件中，属于同一份文档
2. 按 UUID 聚合：同一 UUID 的所有注解（不论来自哪个文件）合并为一个文档节点
3. 算法挂载：通过目录层级、文件关系等算法计算父子关系，生成树形结构
4. 生成输出：每个文档小节附带源代码文件来源，输出 Markdown + sidebar 配置
```

脚本输入/输出：

| 阶段 | 输入                        | 输出                                                                |
| ---- | --------------------------- | ------------------------------------------------------------------- |
| 扫描 | 源码目录路径 + 注解正则规则 | 原始注解列表（UUID, TITLE, SECTION, CONTENT, **sourceFile**, line） |
| 聚合 | 原始注解列表                | 按 UUID 聚合的文档节点（合并跨文件同 UUID 的注解）                  |
| 挂载 | 文档节点树                  | 算法计算父子关系，生成层级结构                                      |
| 生成 | 层级文档树                  | Markdown 文件（每小节带源文件链接）+ VitePress sidebar JSON         |

#### 7.3.4 文档树生成算法思路

```
全局扫描结果（跨所有文件）
  ↓
按 UUID 聚合 → 同一 UUID 不论来自几个文件，合并为一个文档节点
  ↓
TITLE 切割生成目录 → "架构/脚手架/设计思路" → 三层目录结构
  ↓
每个 SECTION 附带源文件信息 → 生成文档时标注“来源: src/xxx/xxx.js"
  ↓
同一 UUID 内的 SECTION 按值自然排序 → "1.概述" < "2.用法" < "3.API"
  ↓
同一 SECTION 内的多行 CONTENT 直接拼接 → Markdown 语法，原样输出
  ↓
输出树形结构 → 生成 Markdown 文件和 sidebar 配置
```

**TITLE 切割示例：**

```
注解：AUTO_DOC_TITLE: 架构/脚手架/设计思路

生成目录结构：
docs/
└── 架构/
    └── 脚手架/
        └── 设计思路.md    ← 文档文件，包含该 UUID 的所有 SECTION
```

同一父目录下多个 TITLE 自动成为同级文档：

```
AUTO_DOC_TITLE: 架构/脚手架/设计思路     → docs/架构/脚手架/设计思路.md
AUTO_DOC_TITLE: 架构/脚手架/目录规范     → docs/架构/脚手架/目录规范.md
AUTO_DOC_TITLE: 架构/装配模式/概述       → docs/架构/装配模式/概述.md

生成：
docs/
└── 架构/
    ├── 脚手架/
    │   ├── 设计思路.md
    │   └── 目录规范.md
    └── 装配模式/
        └── 概述.md
```

**注解代码示例（带序号）：**

 * AUTO_DOC_CONTENT:
 * 提供通用的平台判断工具方法

 * AUTO_DOC_SECTION: 2.使用示例
 * AUTO_DOC_CONTENT:

 * - 需要在 **Quasar 环境**下使用
 * - 通过 `$q.platform.is` 访问

```
#### 7.3.5 与指令集体系的配合

| 场景              | 说明                                                   |
| ----------------- | ------------------------------------------------------ |
| 第 2 层日常开发时 | 新增模块/组件时同步添加注解，文档自动更新              |
| 第 3 层代码检查时 | 脚本可检查注解覆盖率（核心模块是否有注解）             |
| 第 5 层文档生成时 | 注解是文档生成的原料之一，也可结合 AI 补充更详细的描述 |
| 伴生文档站        | VitePress 直接渲染生成的 Markdown，sidebar 自动更新    |

#### 7.3.6 设计决策

| 决策                          | 理由                                                         |
| ----------------------------- | ------------------------------------------------------------ |
| 注解嵌入代码而非独立文件      | 文档与代码同生命周期，代码改了注解就在旁边，不易过期         |
| UUID 作为合并键，跨文件聚合  | 同一实体的注解可分散在多个文件中，全局扫描后按 UUID 合并 |
| SECTION 自然排序               | 作者通过序号控制顺序（1.概述 2.用法），无需额外排序字段   |
| CONTENT 为 Markdown 语法       | 直接拼接生成文档，支持代码块、列表、加粗等富文本         |
| 每个 SECTION 附带源文件链接  | 读者可直接跳转到代码位置，文档与源码可追溯               |
| 算法挂载而非手动指定父子关系 | 百万行代码的项目不可能手动维护文档树，必须自动化             |
| 与 VitePress sidebar 配置联动 | 生成即发布，无需二次手动配置                                 |

### 7.4 伴生文档站的部署与本地开发（建议方案）

> 核心思路：文档站独立部署、独立 CI/CD，本地开发时与主项目并行启动

#### 7.4.1 部署架构

```

主项目仓库 伴生文档站
┌─────────────────┐ ┌─────────────────┐
│ 业务代码 │ │ VitePress 文档 │
│ 自有 CI/CD │ │ 自有 CI/CD │
│ 自有部署流程 │ │ 自有部署流程 │
└─────────────────┘ └─────────────────┘
↑ 注解驱动文档生成（脚本抓取） ↑

````

两者完全独立：

| 维度     | 主项目       | 伴生文档站                        |
| -------- | ------------ | --------------------------------- |
| 部署     | 独立部署流程 | 独立部署流程                      |
| CI/CD    | 自有流水线   | 自有流水线（文档更新触发重建）    |
| 域名     | 业务域名     | 文档专属域名（如 `docs.xxx.com`） |
| 更新触发 | 代码发布     | 注解变更 / 指令集变更 / 手动触发  |

#### 7.4.2 本地开发并行启动

开发时主项目和文档站应同时启动，避免来回切换：

```json
// package.json scripts 示例
{
  "scripts": {
    "dev": "concurrently \"vite\" \"vitepress dev docs\"",
    "dev:app": "vite",
    "dev:docs": "vitepress dev docs"
  }
}
````

| 命令            | 行为                    |
| --------------- | ----------------------- |
| `pnpm dev`      | 并行启动主项目 + 文档站 |
| `pnpm dev:app`  | 只启动主项目            |
| `pnpm dev:docs` | 只启动文档站            |

#### 7.4.3 触发文档重建的时机

| 触发方式   | 说明                                                                             |
| ---------- | -------------------------------------------------------------------------------- |
| 注解变更   | 代码中 `AUTO_DOC_` 注解增删改时，脚本自动重新生成文档（可集成到 Git hook 或 CI） |
| 指令集变更 | `ai-instructions/` 目录有 commit 时，触发文档站重建                              |
| 手动触发   | 执行 `pnpm docs:build` 手动重新扫描注解并生成文档                                |

### 7.5 指令执行模型与落地路线图（建议方案）

> 核心思路：各层指令独立执行，需要串联时用编排文件组合，不强制全局顺序

#### 7.5.1 执行独立性原则

每条指令默认独立执行，不依赖其他指令的运行结果。使用者从入口文件选中对应指令直接调用即可。

```
入口文件 (entry.md)
  ├── 直接执行：选中哪条跑哪条，互不依赖
  └── 编排执行：通过编排文件按顺序调用多条指令
```

#### 7.5.2 三种执行模式

| 模式       | 适用场景                                 | 实现方式                       |
| ---------- | ---------------------------------------- | ------------------------------ |
| 单指令执行 | 日常最高频场景，做一件事就调一条指令     | 从 `entry.md` 选中直接执行     |
| 内嵌步骤   | 某条指令的流程固定包含几个阶段           | 在指令文件内部追加步骤，不拆分 |
| 编排执行   | 需要跨指令串联（如：检查 → 修复 → 复检） | 写编排文件，内部调度现有指令   |

#### 7.5.3 编排文件设计

编排文件是“调度器”，不重复实现指令逻辑，只负责按顺序调用：

```
ai-instructions/
├── layer-2-dev/
│   ├── entry.md
│   ├── new-feature.md           # 单指令
│   └── ...
├── pipelines/                    # 编排文件目录
│   ├── feature-complete.md       # 示例：新功能完整流程
│   └── pre-release-check.md      # 示例：上线前完整检查
```

编排文件示例（`pipelines/feature-complete.md`）：

```markdown
# 新功能完整流程

## 执行步骤

1. 执行 `layer-1-context/entry.md` → 加载基础上下文
2. 执行 `layer-2-dev/new-feature.md` → 开发新功能（参数：module=xxx）
3. 执行 `layer-3-code-review/entry.md` → 代码检查（参数：scope=刚修改的模块）
4. 执行 `layer-2-dev/self-check.md` → 模块自检（参数：module=xxx）

## 步骤间传递

- 步骤 2 的输出（修改的文件列表）作为步骤 3 的 scope 参数
- 步骤 3 发现的问题作为步骤 4 的检查重点
```

#### 7.5.4 编排 vs 内嵌的选择原则

| 情况                           | 选择         | 理由                         |
| ------------------------------ | ------------ | ---------------------------- |
| 步骤固定、只会这一种组合       | 内嵌步骤     | 简单直接，不需要额外文件     |
| 步骤可能变化、不同场景组合不同 | 编排文件     | 灵活组合，复用现有指令       |
| 临时性的一次性流程             | 临时编排文件 | 用完即弃，不污染正式指令     |
| 需要参数在步骤间传递           | 编排文件     | 编排文件可以显式定义传递规则 |

#### 7.5.5 落地路线图建议

按价值优先级排序，先做高频高价值的：

| 优先级 | 层级               | 理由                           |
| ------ | ------------------ | ------------------------------ |
| P0     | 第 1 层 基础提示词 | 所有其他层的基础，必须先有     |
| P0     | 第 2 层 日常开发   | 使用频率最高，直接影响开发效率 |
| P1     | 第 3 层 代码检查   | 配合日常开发，保证代码质量     |
| P1     | 第 4 层 上线检查   | 每次上线都需要，风险最低点     |
| P2     | 第 5 层 文档生成   | 有价值但非紧急，可逐步完善     |
| P2     | 第 0 层 健康度巡检 | 长期价值，定期执行即可         |
| P3     | 编排文件           | 待各层指令稳定后再编排串联     |
