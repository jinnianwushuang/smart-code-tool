# 执行模型与编排

> 各层指令独立执行，需要串联时用编排文件组合，不强制全局顺序

---

## 执行独立性原则

每条指令默认独立执行，不依赖其他指令的运行结果。使用者从入口文件选中对应指令直接调用即可。

```
入口文件 (entry.md)
  ├── 直接执行：选中哪条跑哪条，互不依赖
  └── 编排执行：通过编排文件按顺序调用多条指令
```

---

## 三种执行模式

| 模式       | 适用场景                                 | 实现方式                       |
| ---------- | ---------------------------------------- | ------------------------------ |
| 单指令执行 | 日常最高频场景，做一件事就调一条指令     | 从 `entry.md` 选中直接执行     |
| 内嵌步骤   | 某条指令的流程固定包含几个阶段           | 在指令文件内部追加步骤，不拆分 |
| 编排执行   | 需要跨指令串联（如：检查 → 修复 → 复检） | 写编排文件，内部调度现有指令   |

---

## 编排文件设计

编排文件是"调度器"，不重复实现指令逻辑，只负责按顺序调用：

```
ai-instructions/
├── layer-3-dev/
│   ├── entry.md
│   ├── new-feature.md           # 单指令
│   └── ...
├── pipelines/                    # 编排文件目录
│   ├── feature-complete.md       # 示例：新功能完整流程
│   └── pre-release-check.md      # 示例：上线前完整检查
```

### 编排文件示例

```markdown
# 新功能完整流程

## 执行步骤

1. 执行 `layer-2-context/entry.md` → 加载基础上下文
2. 执行 `layer-3-dev/new-feature.md` → 开发新功能（参数：module=xxx）
3. 执行 `layer-4-code-review/entry.md` → 代码检查（参数：scope=刚修改的模块）
4. 执行 `layer-3-dev/self-check.md` → 模块自检（参数：module=xxx）

## 步骤间传递

- 步骤 2 的输出（修改的文件列表）作为步骤 3 的 scope 参数
- 步骤 3 发现的问题作为步骤 4 的检查重点
```

---

## 编排 vs 内嵌的选择原则

| 情况                           | 选择         | 理由                         |
| ------------------------------ | ------------ | ---------------------------- |
| 步骤固定、只会这一种组合       | 内嵌步骤     | 简单直接，不需要额外文件     |
| 步骤可能变化、不同场景组合不同 | 编排文件     | 灵活组合，复用现有指令       |
| 临时性的一次性流程             | 临时编排文件 | 用完即弃，不污染正式指令     |
| 需要参数在步骤间传递           | 编排文件     | 编排文件可以显式定义传递规则 |

---

## 落地路线图

按价值优先级排序，先做高频高价值的：

| 优先级 | 层级               | 理由                           |
| ------ | ------------------ | ------------------------------ |
| P0     | 第 2 层 基础提示词 | 所有其他层的基础，必须先有     |
| P0     | 第 3 层 日常开发   | 使用频率最高，直接影响开发效率 |
| P1     | 第 4 层 代码检查   | 配合日常开发，保证代码质量     |
| P1     | 第 5 层 上线检查   | 每次上线都需要，风险最低点     |
| P2     | 第 6 层 文档生成   | 有价值但非紧急，可逐步完善     |
| P2     | 第 1 层 健康度巡检 | 长期价值，定期执行即可         |
| P3     | 编排文件           | 待各层指令稳定后再编排串联     |

## 伴生文档站部署

### 部署架构

主项目和伴生文档站完全独立：

| 维度     | 主项目       | 伴生文档站                       |
| -------- | ------------ | -------------------------------- |
| 部署     | 独立部署流程 | 独立部署流程                     |
| CI/CD    | 自有流水线   | 自有流水线（文档更新触发重建）   |
| 域名     | 业务域名     | 文档专属域名                     |
| 更新触发 | 代码发布     | 注解变更 / 指令集变更 / 手动触发 |

### 本地开发并行启动

开发时主项目和文档站应同时启动：

```json
{
  "scripts": {
    "dev": "concurrently \"vite\" \"vitepress dev docs\"",
    "dev:app": "vite",
    "dev:docs": "vitepress dev docs"
  }
}
```

### 触发文档重建的时机

| 触发方式   | 说明                                                  |
| ---------- | ----------------------------------------------------- |
| 注解变更   | 代码中 `AUTO_DOC_` 注解增删改时，脚本自动重新生成文档 |
| 指令集变更 | `ai-instructions/` 目录有 commit 时，触发文档站重建   |
| 手动触发   | 执行 `pnpm docs:build` 手动重新扫描注解并生成文档     |
