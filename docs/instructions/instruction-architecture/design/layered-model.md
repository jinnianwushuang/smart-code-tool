# 分层模型设计

> 六层指令体系的定义、边界与落地要点

---

## 设计背景

企业级项目的 AI 辅助开发面临以下挑战：

- 不同场景需要不同类型的指令（开发、检查、文档）
- 指令的使用频率差异大（有的每天用，有的每周用）
- 大项目和小项目的覆盖需求不同
- 多人协作需要统一标准

分层设计让每层专注一个维度，互不干扰，按需组合。

---

## 六层定义

### 第 1 层：项目健康度巡检

**定位**：定期执行，偏运维治理

**执行内容**：

- 依赖版本检查（是否有已知漏洞、版本过旧）
- 废弃 API 使用扫描
- 测试覆盖率趋势分析
- 输出与上次报告的对比报告

**参数需求**：可选（默认全量，可指定模块范围）

**落地要点**：

- 输出报告需记录时间和位置，支持历史回溯
- 对比报告量化变化（新增 N 个警告、修复 M 个问题）

---

### 第 2 层：基础提示词

**定位**：固定前置，AI 的"项目认知手册"

**执行内容**：

- 技术栈声明（框架、UI 库、构建工具版本）
- 目录结构约定与模块索引
- 命名规范
- 核心架构模式说明
- 团队红线（禁止事项）

**参数需求**：无（固定流程，直接加载全部上下文）

**落地要点**：

- 可直接作为新成员入职的项目认知手册
- 需要明确指定作用域（哪些文件/目录）
- 模块索引文件让 AI 知道"去哪找什么"，避免盲目搜索

---

### 第 3 层：日常开发模块级别

**定位**：高频使用，贴合架构的日常开发

**执行内容**：

- 新功能开发指令
- 重构指令
- 迭代修改指令
- Bug 修复指令
- 模块自检指令

**参数需求**：必须（模块路径、组件名、任务类型等）

**落地要点**：

- 按模块/功能域拆分，每个指令独立可执行
- 保持"轻而准"，不要一个大文件涵盖所有
- 每个指令附带前置条件说明

---

### 第 4 层：项目级代码检查

**定位**：插件 + AI 互补

**执行内容**：

- 插件检查项引用（ESLint / Prettier 等已有工具的引用）
- AI 补充检查项（插件无法覆盖的维度）：
  - 业务逻辑一致性
  - 跨模块依赖合理性
  - 命名语义准确性

**参数需求**：可选（默认全项目，可指定文件/目录范围）

**落地要点**：

- ESLint / Prettier 等能做的，不写进指令集
- AI 聚焦在插件无法分析的维度

**业务扩展指令**：

研发在执行代码检查过程中，AI 助手可能发现缺少针对特定业务场景的检查规则。此时 AI 应在 `custom/` 目录下追加新的检查指令文件，并自动更新入口索引。这些业务级检查指令会在使用中持续自我进化。

详见 → [业务扩展指令机制](#业务扩展指令机制)

---

### 第 5 层：版本上线前核心功能检查

**定位**：核心功能不能出错

**执行内容**：

- 按核心功能清单逐项检查
- 输出检查报告

**参数需求**：无（固定流程，按清单逐项执行）

**落地要点**：

- 维护一份核心功能清单（而非每次临时列）
- 可与 CI/CD 流水线联动

---

### 第 6 层：文档生成

**定位**：按需生成**详细文档目录树**，而非一个事项一个简单 wiki

**核心原则**：

文档生成的价值在于产出**体系化的文档目录结构**，而不是零散的单个 wiki 页面。每次生成应先规划完整的文档目录树，再逐节点填充内容，确保文档具备层次感和可导航性。

**执行内容**：

- 业务线文档目录树生成（模块 → 子模块 → 接口 → 详细说明）
- 架构文档目录树生成（系统 → 子系统 → 模块 → 组件 → 关系）
- 流程图生成（嵌入到对应目录节点中）
- 注释代码文档生成（按模块聚合，非零散罗列）

**参数需求**：必须（文档类型、作用域、输出位置、目录深度）

**落地要点**：

- **先目录后内容**：先生成完整的文档目录树（含层级、标题、摘要），确认后再逐节点填充
- **目录即导航**：生成的文档目录树本身就是一个可导航的索引页，读者能快速定位所需内容
- **深度可控**：通过参数控制目录深度（如 2 级概览 vs 4 级详细），避免过浅无价值或过深难维护
- 区分"给人看的"和"给 AI 后续消费的结构化文档"
- 代码注解（AUTO_DOC）是文档生成的重要原料

**反面模式**：

```
❌ 一个事项一个简单 wiki：
  api-doc.md        ← 所有 API 平铺在一个文件
  state-doc.md      ← 所有状态管理平铺在一个文件

✅ 详细文档目录树：
  docs/
  ├── index.md                ← 文档目录总索引
  ├── api/
  │   ├── index.md            ← API 总览
  │   ├── user-api.md         ← 用户模块 API
  │   ├── order-api.md        ← 订单模块 API
  │   └── payment-api.md      ← 支付模块 API
  ├── architecture/
  │   ├── index.md            ← 架构总览
  │   ├── module-dependency.md← 模块依赖关系
  │   └── data-flow.md        ← 数据流图
  └── state/
      ├── index.md            ← 状态管理总览
      └── order-state.md      ← 订单状态机
```

**业务扩展指令**：

研发在文档生成过程中，AI 助手可能发现缺少特定业务领域的文档生成模板（如特定格式的 API 文档、业务状态机文档等）。此时 AI 应在 `custom/` 目录下追加新的生成指令文件，并自动更新入口索引。这些业务级生成指令会在使用中持续自我进化。

详见 → [业务扩展指令机制](#业务扩展指令机制)

## 层间关系

```
第 2 层（基础提示词）→ 为所有层提供上下文
第 3 层（日常开发）  → 开发时产生代码变更和注解
第 4 层（代码检查）  → 检查第 3 层的产出
第 5 层（上线检查）  → 上线前验证核心功能
第 6 层（文档生成）  → 基于代码和注解生成文档
第 1 层（健康巡检）  → 独立运行，定期体检
```

各层**默认独立执行**，需要串联时通过编排文件（pipelines/）组合。

## 报告输出架构

指令集与报告输出必须分离为两个独立根目录，而不是将报告混在指令集目录内。

### 设计动机

- 指令集是“规则”，报告是“产出”，两者职责不同，混在一起会造成目录污染
- 项目文档站点需要集成报告内容，报告目录即文档站点的菜单树数据源
- 报告是动态生成的，菜单树也需动态生成，因此报告目录结构必须规范可预测

### 目录分离规则

```
项目根目录/
├── ai-instructions/          # 指令集（规则，拷贝到目标项目）
│   ├── layer-4-code-review/  # 第 4 层指令
│   └── layer-6-docs/         # 第 6 层指令
│
└── ai-reports/               # 报告输出（产出，不拷贝）
    ├── layer-1-health/       # 第 1 层报告
    ├── layer-4-code-review/  # 第 4 层报告
    ├── layer-5-release/      # 第 5 层报告
    └── layer-6-docs/         # 第 6 层文档
        ├── api/              # 每条指令有固定输出子目录
        └── architecture/
```

### 各层报告输出规则

| 层级    | 输出目录                          | 归档策略                    | 说明                                   |
| ------- | --------------------------------- | --------------------------- | -------------------------------------- |
| 第 1 层 | `ai-reports/layer-1-health/`      | 按执行日期（`YYYY-MM-DD/`） | 每次巡检生成带日期的报告目录           |
| 第 4 层 | `ai-reports/layer-4-code-review/` | 按执行日期                  | 每次检查生成报告，支持历史对比         |
| 第 5 层 | `ai-reports/layer-5-release/`     | 按版本号（`v1.2.0/`）       | 每次上线生成对应版本的检查报告         |
| 第 6 层 | `ai-reports/layer-6-docs/`        | 按文档类型分目录            | 每个指令有固定输出子目录，内容覆盖更新 |

### 文档站点动态菜单集成

报告目录结构直接映射为文档站点的菜单树，实现「报告即文档」：

```
文档站点构建流程
1. 扫描 ai-reports/ 目录结构
2. 每个子目录 → 菜单分组
3. 每个 .md 文件 → 菜单页面
4. index.md → 分组概览页
5. 动态生成完整菜单树，无需手动配置
```

**核心特性**：

| 特性       | 说明                                       |
| ---------- | ------------------------------------------ |
| 目录即菜单 | 目录结构直接映射菜单树，无需额外配置       |
| 新增即出现 | 新报告输出到新目录后，菜单自动出现对应条目 |
| 删除即消失 | 报告过期删除后，菜单条目自动消失           |
| 归档即分组 | 按日期/版本号归档的子目录自动成为菜单分组  |

## 大项目特殊考量

针对几十万行、百万行代码的项目：

1. **模块索引优先**：通过模块索引文件引导 AI 定位，而非全量扫描
2. **指令拆分粒度**：大模块需进一步拆分为子指令，单次覆盖范围可控
3. **结果可追溯**：所有执行结果持久化存储，支持历史回溯
4. **增量执行**：支持只处理变更部分（结合 Git diff）

## 业务扩展指令机制

第 4 层（代码检查）和第 6 层（文档生成）支持**业务扩展指令**机制，允许在实际使用过程中由 AI 助手动态追加和进化指令。

### 设计动机

- 预设指令无法覆盖所有业务场景，研发过程中会不断出现新的检查/生成需求
- AI 助手在执行任务时最容易发现"缺少什么指令"，应由其主动补充
- 这些指令需要在使用中反复打磨，自我进化

### 目录结构

每层的 `custom/` 子目录用于存放业务扩展指令：

```
layer-4-code-review/
├── custom/                        ← 业务扩展指令区
│   ├── index.md                   ← 入口汇总（自动维护）
│   ├── check-api-consistency.md   ← 单个业务指令文件
│   ├── check-state-flow.md        ← 单个业务指令文件
│   └── ...
├── entry.md                       ← 第 4 层主入口
└── ...                            ← 其他预设指令文件

layer-6-docs/
├── custom/                        ← 业务扩展指令区
│   ├── index.md                   ← 入口汇总（自动维护）
│   ├── gen-api-doc.md             ← 单个业务指令文件
│   ├── gen-state-machine-doc.md   ← 单个业务指令文件
│   └── ...
├── entry.md                       ← 第 6 层主入口
└── ...                            ← 其他预设指令文件
```

### 核心规则

| 规则         | 说明                                                                          |
| ------------ | ----------------------------------------------------------------------------- |
| 一指令一文件 | 每个业务扩展指令独立一个 `.md` 文件，不合并                                   |
| 入口自动聚合 | `custom/index.md` 作为汇总入口，列出所有扩展指令的标题、用途、创建时间        |
| AI 主动追加  | AI 在执行中发现缺少指令时，主动创建新文件并更新 `index.md`                    |
| 自我进化     | AI 在执行指令后，可根据执行结果优化指令内容（更新步骤、补充检查项、修正参数） |
| 版本标记     | 每个扩展指令文件头部标注 `created` 和 `last_evolved` 时间戳                   |
| 不污染预设   | 扩展指令与预设指令物理隔离，互不干扰                                          |

### 指令文件格式

每个业务扩展指令文件须遵循统一格式：

```markdown
---
title: <指令标题>
layer: <所属层级，如 layer-4>
created: YYYY-MM-DD
last_evolved: YYYY-MM-DD
evolved_count: <进化次数>
source: ai | human
---

# <指令标题>

## 适用场景

<描述什么情况下触发此指令>

## 执行步骤

1. ...
2. ...

## 检查项 / 输出格式

- ...

## 进化记录

- YYYY-MM-DD: <本次进化内容>
```

### 自我进化流程

```
AI 执行某条扩展指令
  → 执行完成后评估结果
  → 发现指令有遗漏或可优化
  → 直接修改该指令文件（更新步骤/检查项/参数）
  → 更新 last_evolved 时间戳和 evolved_count
  → 在「进化记录」中追加本次变更说明
```

## 单人项目的价值

即便是单人维护的项目，成套指令集同样有价值：

- 较长时间后再次维护时，快速恢复项目知识脉络
- 基础提示词 = 项目记忆，不会遗忘
- 核心功能检查清单 = 上线前的安全网
- 文档生成 = 降低"只有自己能看懂"的风险
- 业务扩展指令 = 项目经验的持续沉淀，越用越精准
