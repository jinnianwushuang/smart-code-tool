# 多工作区组合开发套件

> 本文讨论一种基于 VSCode 多根工作区（Multi-root Workspace）能力，将多个项目按职责分层组合为**可组合开发套件**的思路。
> 核心目标：让 AI 助手在开发时能同时获取**接口契约、架构范式、业务上下文**三层信息，从而给出更精准的代码和建议。

---

## 核心问题

当前 AI 辅助开发的主要痛点：

1. **上下文割裂**：AI 只能看到当前项目的代码，不了解接口契约、架构规范等外部约束
2. **指令集孤立**：指令集放在项目内部，无法区分「通用架构规范」和「业务特定逻辑」
3. **接口信息缺失**：AI 不知道前端字段对应后端的哪些接口定义，导致生成代码与实际数据脱节

如果能让 AI 同时加载**接口层 + 架构层 + 业务层**的完整链路上下文，重构代码和开发需求的输出质量将显著提升。

---

## 仓体结构

套件项目（接口层 + 各框架架构层 + 总调度）本身都不大，且全是 Markdown + JSON 配置类文件，采用**单仓包裹**更便于协调调度。主项目（业务层）作为实际商业项目保持**独立仓**。

```
smart-dev-kit/                          ← 单仓（套件项目全部在内）
├── api-archive/                  ← 接口层（数据存档 + 服务 + SDK）
├── api-web/                      ← 接口可视化（独立前端项目）
├── vue-instructions/             ← 架构层（Vue）
├── react-instructions/           ← 架构层（React）
├── flutter-instructions/         ← 架构层（Flutter）
├── dispatcher/                   ← 总调度（AI 入口编排）
├── scripts/                      ← Google ZX 脚本（服务拉起）
└── smart-dev-kit.code-workspace        ← VSCode 多根工作区配置

my-business-app/                  ← 主项目（独立仓）
├── src/
├── business-instructions/        ← 业务指令集
├── api-mapping.md                ← 接口映射文件
└── ai-entry.md                   ← AI 理解入口
```

两者通过 **VSCode 多根工作区**关联：开发者在主项目中将 smart-dev-kit 目录添加到工作区即可。

## 三项目分层模型

按职责拆分为三个逻辑项目，形成可组合的开发套件：

```
┌───────────────────────────────────────────────────────────────┐
│                     VSCode 多根工作区                          │
│                                                               │
│  ┌────────────────────────────────┐  ┌─────────────────────┐  │
│  │  smart-dev-kit/（单仓）               │  │  主项目/（独立仓）   │  │
│  │                                │  │                     │  │
│  │  ┌──────────────────────────┐  │  │  业务代码            │  │
│  │  │ api-archive/  (接口层)   │  │  │  业务指令集          │  │
│  │  │  ├─ archives/           │  │  │  接口映射文件         │  │
│  │  │  ├─ schemas/  (字段解释) │  │  │  ai-entry.md         │  │
│  │  │  ├─ mappings/           │  │  │                     │  │
│  │  │  ├─ constraints/        │  │  │                     │  │
│  │  │  ├─ sdk/                │←─┼──┼─ SDK 手动拷贝        │  │
│  │  │  └─ server/ (Fastify)   │  │  │                     │  │
│  │  ├──────────────────────────┤  │  │  ← HTTP 实例挂载 SDK │  │
│  │  │ api-web/ (接口可视化)    │  │  │    自动上报接口数据   │  │
│  │  ├──────────────────────────┤  │  │                     │  │
│  │  │ vue-instructions/       │  │  └─────────────────────┘  │
│  │  │ react-instructions/     │  │                           │
│  │  │ flutter-instructions/   │  │                           │
│  │  ├──────────────────────────┤  │                           │
│  │  │ dispatcher/ (总调度)     │  │                           │
│  │  │ scripts/    (ZX 服务)    │  │                           │
│  │  └──────────────────────────┘  │                           │
│  └────────────────────────────────┘                           │
└───────────────────────────────────────────────────────────────┘
```

### 接口层 — api-archive/

**定位**：本地 API 备份存档 + 字段解释 + 服务 + SDK，类似轻量版 YAPI 的数据底座。

**职责**：

- **archives/**：存档后端接口的原始请求/响应 JSON，按 **projectId** 区分根目录
- **schemas/**：每个接口单独一个字段解释文件（字段类型、说明、枚举值、是否必填），由 SDK + CLI + AI 三级链路自动生成
- **constraints/**：提供格式约束，统一规范映射文件和 schema 的结构
- **server/**：内置 **Fastify 本地服务**，接收 SDK 上报数据、提供接口查询 API、防抖落盘
- **sdk/**：内置 **SDK**，供主项目手动拷贝后挂载到 HTTP 实例上自动上报
- 提供 AI 助手的**理解入口文件**

**核心价值**：

- AI 在生成前端代码时，能直接参照真实的接口数据结构和字段说明
- 接口变更时，通过映射文件可快速定位受影响的前端模块
- 框架无关，一次维护多框架共用

### 接口可视化 — api-web/

**定位**：独立前端项目，类似 YAPI 的 Web UI，是日常启动的**人面向入口**。

**职责**：

- **接口浏览**：按项目 → 模块 → 接口三级树形浏览，展示字段类型、说明、枚举值
- **变更对比**：对比不同时间的接口存档，高亮变更字段
- **映射预览**：查看前端调用位置与接口的映射关系
- **KIT 使用指南**：提供使用这套开发套件的步骤说明、AI 指令语句（可直接复制）
- **SDK 对接文档**：提供 SDK 集成指南、代码示例、配置说明
- **在线部署**：团队成员共用一个服务，不依赖本地 Fastify

**日常启动**：开发者日常启动的是 Fastify 服务 + api-web 前端，api-web 通过路由提供指引和使用说明。

**核心价值**：

- 没有 Web UI，纯 JSON 文件浏览接口不现实，api-web 让人能直观查看和管理接口
- 内置 KIT 使用指南和 AI 指令语句，新成员打开 api-web 即可了解整套工作流
- 可在线部署，团队共享接口存档

### 架构层 — *-instructions/

**定位**：框架级通用指令集，包含**除业务逻辑外**的所有架构规范和标准范式。每个框架一个平级目录，互不干扰。

**职责**：

- 提供标准架构范式代码指令（如装配架构、代码检查、代码模板等）
- 提供约束文件（constraints）定义版本基线、编码约定、架构规范
- 提供提示词集（prompts + constraints）
- 提供与主项目的**对接入口文件**，使业务层指令集可引用架构层规范
- 提供 AI 助手的**理解入口文件**

**核心价值**：

- 架构规范与业务逻辑解耦，可跨项目复用
- 新项目只需拷贝架构层 + 配置业务指令集，即可快速获得 AI 辅助开发能力

### 业务层 — 主项目（独立仓）

**定位**：实际开发的主项目，任何一个商业项目，保持独立仓独立版本管理。

**职责**：

- 内部提供**业务逻辑检查指令集**（业务规则、领域模型、数据校验等）
- 内部提供**业务逻辑文档性指令集**（业务流程说明、领域术语表等）
- 提供与架构层的 AI 指令集**对接入口文件**
- 提供与接口层对接的**接口字段映射文件**（代码路径 → 接口 → 字段函数模块对应关系）
- 在 HTTP 实例（如 axios 封装处）挂载 SDK，传入实例 + 项目标识，自动上报接口数据
- 提供 AI 助手的**理解入口文件**

**核心价值**：

- 业务指令集只关注领域逻辑，不重复声明架构规范
- 通过映射文件让 AI 理解「这段代码调用了哪个接口、字段含义是什么」
- 独立仓管理，不受套件版本影响

### 总调度 — dispatcher/

**定位**：AI 入口编排中心，负责串联三层上下文。

**职责**：

- 根据当前主项目的框架类型，决定加载哪个框架的指令集
- 编排 AI 入口文件的加载顺序（先架构层 → 再业务层 → 最后接口层）
- 提供 AI 助手的**总入口文件**

**注意**：dispatcher 只管调度和入口编排，**不负责服务启停**（服务由根目录 ZX 脚本拉起）。

## 三项目协作链路

AI 助手加载上下文时的信息流转：

```
AI 助手启动
  │
  ├─→ 读取项目三入口文件（业务上下文 + 领域模型）
  │     │
  │     ├─→ 通过对接入口 → 加载项目二架构指令集
  │     │     （架构范式 + 编码约束 + 标准规范）
  │     │
  │     └─→ 通过映射文件 → 查询项目一接口存档
  │           （接口定义 + 字段含义 + 数据结构）
  │
  └─→ 三层上下文就绪，开始辅助开发
```

**最终效果**：AI 同时理解「接口长什么样」「架构该怎么写」「业务逻辑是什么」，代码生成和重构建议的质量显著提升。

## 跨框架复用分析

三个框架（Vue / React / Flutter）采用相同的三项目模型，但存在复用关系：

| 项目层级 | 定位   | Vue                 | React                 | Flutter                 | 是否跨框架共用 |
| -------- | ------ | ------------------- | --------------------- | ----------------------- | -------------- |
| 项目一   | 接口层 | API 存档 + 映射     | API 存档 + 映射       | API 存档 + 映射         | ✅ 可共用      |
| 项目二   | 架构层 | Vue 指令集          | React 指令集          | Flutter 指令集          | ❌ 框架专属    |
| 项目三   | 业务层 | Vue 业务指令 + 映射 | React 业务指令 + 映射 | Flutter 业务指令 + 映射 | ❌ 项目专属    |

**关键发现**：

- **项目一可跨框架共用**：接口定义是框架无关的，同一个后端 API 存档可同时服务于 Vue、React、Flutter 三个前端项目
- **项目二按框架隔离**：架构指令集与框架强绑定（Vue 用装配架构、React 用 Hooks 架构、Flutter 用 GetX 架构）
- **项目三按业务隔离**：每个商业项目有独立的业务逻辑指令集

## VSCode 多根工作区的角色

VSCode 的 Multi-root Workspace 是本方案的**载体**，将 smart-dev-kit 单仓和主项目独立仓组合到同一工作区：

```jsonc
// smart-dev-kit.code-workspace（位于 smart-dev-kit 根目录）
{
  "folders": [
    { "path": ".", "name": "📦 Dev Kit" },
    { "path": "../my-business-app", "name": "💼 主项目" },
  ],
  "settings": {
    // 各目录的独立配置互不干扰
  },
}
```

**优势**：

- smart-dev-kit 单仓管理套件项目，一次 `git clone` 拿到全部
- 主项目保持独立仓，不受套件版本影响
- VSCode 的文件搜索、终端、调试等功能可同时覆盖所有项目
- AI 助手（如 Cursor、Copilot）可索引整个工作区的文件作为上下文

## 可组合性设计

三项目模型的核心价值在于**可组合**：

### 水平组合（同一框架，不同业务项目）

```
                    ┌─ 业务项目 A（电商）
接口存档（共用）───┤
架构指令集（共用）──┤
                    └─ 业务项目 B（CRM）
```

同一套接口存档 + 架构指令集，可搭配不同的业务项目，快速组建多个开发套件。

### 垂直组合（同一业务，不同框架）

```
                    ┌─ Vue 架构指令集
接口存档（共用）───┤─ React 架构指令集
                    └─ Flutter 架构指令集
业务指令集（共用）───┘
```

同一个后端 API + 同一套业务逻辑，可同时服务于三个前端框架的开发。

## SDK 与自动上报机制

### SDK 引用方式

SDK 采用**手动拷贝**方式集成到主项目，不通过 npm 管理。因为结构简单，固定一次成型后很少变动。

```
主项目 utils/
└── api-reporter/          ← 从 smart-dev-kit/api-archive/sdk/ 手动拷贝
    ├── index.js
    ├── reporter.js
    └── types.d.ts
```

### 上报挂载方式

在主项目的 HTTP 实例封装处（如 axios 实例），调用 SDK 传入实例和项目标识：

```js
// 主项目 src/utils/request.js（axios 实例封装处）
import { createReporter } from './api-reporter'

const axiosInstance = axios.create({ baseURL: '...' })

// 传入实例 + 项目标识，SDK 自动拦截请求/响应并上报
createReporter(axiosInstance, {
  projectId: 'my-ecommerce-app',
  mode: 'http', // 或 'ws'
})
```

WebSocket 同理，传入 WS 实例即可：

```js
createReporter(wsInstance, {
  projectId: 'my-ecommerce-app',
  mode: 'ws',
})
```

### 存档按项目隔离

API 存档按 **projectId** 区分根目录，多个主项目共用同一个 smart-dev-kit 而存档互不干扰：

```
api-archive/archives/
├── my-ecommerce-app/          ← 项目标识作为根目录
│   ├── user/
│   │   ├── GET_user_info.json
│   │   └── PUT_user_update.json
│   └── order/
│       └── GET_order_list.json
│
├── my-crm-app/                ← 另一个项目
│   ├── customer/
│   └── ticket/
│
└── my-admin-panel/            ← 又一个项目
    └── ...
```

### 服务端防抖与延迟批量写入

SDK 只管往服务端丢数据，服务端（Fastify）自己决定什么时候落盘。调用方零心智负担。

```
上报请求 1 ──┐
上报请求 2 ──┤
上报请求 3 ──┼──→ Fastify 服务端 ──→ 防抖窗口到期 ──→ 批量写入 archives/ + schemas/ + mapping
上报请求 4 ──┤
上报请求 5 ──┘
```

服务端内部防抖机制：收到上报数据后不立即写磁盘，而是在防抖窗口内累积一批数据，窗口到期后批量写入 `archives/` 并触发 schema 和映射文件重新生成。

## Schema 字段解释自动生成

每个接口单独一个 schema 文件，存放字段类型、说明、枚举值等信息，用于 api-web 展示和 AI 上下文增强。

```
api-archive/schemas/
└── my-ecommerce-app/
    └── user/
        └── GET_user_info.json    ← 每个接口单独一个文件
```

### 三级自动生成链路

字段解释**不人工填写**，通过三级链路自动生成：

```
① SDK 上报 ──→ Fastify 收到原始 JSON
     │
     ├─→ 自动推断字段类型，生成 schema 骨架
     │   （字段名 + type，description 留空）
     │
② CLI 命令 ──→ npm run fix-schemas
     │
     ├─→ 对比 archives/ 与 schemas/ 的差异
     ├─→ 新增字段补入骨架
     ├─→ 删除字段标记 deprecated
     └─→ 类型变更标记 conflict
     │
③ AI 指令 ──→ 主项目反向丰富
     │
     ├─→ AI 读取主项目业务代码
     ├─→ 理解每个字段在业务中的含义
     ├─→ 自动回填 description、enum、业务规则
     └─→ 写回 schemas/ 对应文件
```

- **第①级**：SDK 上报时自动生成骨架，零人工介入
- **第②级**：CLI 命令强制修复，处理字段变更、类型冲突
- **第③级**：AI 指令驱动，从主项目业务代码中**反向推导**字段含义，自动丰富说明——AI 同时看到接口数据和业务代码，能给出最准确的字段解释

## 服务拉起与职责分离

| 角色                                | 工具               | 职责                                                            |
| ----------------------------------- | ------------------ | --------------------------------------------------------------- |
| **ZX 脚本**（smart-dev-kit 根目录） | Google ZX          | 拉起 Fastify 服务 + api-web 开发服务、调度任务、CLI 命令        |
| **dispatcher**                      | 纯 Markdown + 配置 | AI 入口编排、加载顺序声明、框架路由                             |
| **Fastify server**                  | Fastify            | 提供接口查询 API、接收上报数据、存档读写、防抖落盘、schema 生成 |
| **api-web**                         | Vite + Vue/React   | 接口可视化浏览、KIT 使用指南、SDK 对接文档、AI 指令语句展示     |

```js
#!/usr/bin/env zx
// smart-dev-kit/scripts/start.mjs

// 启动 Fastify 服务
await $`node api-archive/server/index.js`

// CLI 命令
// npm run start               — 启动服务
// npm run sync-mapping         — 手动触发映射文件生成
// npm run generate-mapping <projectId> — 生成指定项目的映射文件
```

## 对接机制

三项目之间的对接通过**映射文件**和**入口文件**实现，而非代码级别的依赖：

### 接口层 ↔ 业务层：接口映射文件

```
# api-mapping.md（位于主项目内部）

## 用户模块接口映射

| 前端调用位置              | 接口路径              | 关键字段映射                    |
| ------------------------- | --------------------- | ------------------------------- |
| src/api/user.ts → getUser | GET /api/user/info    | nickname → userName, avatar → … |
| src/api/user.ts → update  | PUT /api/user/update  | ...                             |
```

### 架构层 → 业务层：架构对接入口

```
# arch-entry.md（位于主项目内部）

## 架构规范引用

本项目遵循 Vue 装配架构指令集规范。
架构指令集路径：[smart-dev-kit]/vue-instructions/vue-assembler/
约束文件路径：[smart-dev-kit]/vue-instructions/constraints.md
```

### AI 入口文件

每个逻辑项目提供一个 `ai-entry.md`，作为 AI 助手理解该项目角色的入口：

```
# ai-entry.md（位于主项目内部）

## 本项目角色
本项目是业务层主项目，包含电商业务的 Vue 3 前端代码。

## 上下文引用
- 总调度入口：请参阅 [smart-dev-kit]/dispatcher/entry.md
- 接口存档：请参阅 [smart-dev-kit]/api-archive/ai-entry.md
- 架构规范：请参阅 [smart-dev-kit]/vue-instructions/ai-entry.md
- 接口映射：请参阅 [接口映射文件](./api-mapping.md)
```

## 与现有指令集体系的关系

本方案**不改变**现有指令集的内部结构，而是在其之上增加一层**工作区组合**的视角：

| 层面           | 现有体系                          | 本方案新增                 |
| -------------- | --------------------------------- | -------------------------- |
| 指令集内部     | 三层模型（docs + AI 指令 + 模板） | 不变                       |
| 指令集之间     | 通过 kit.zip 打包分发             | 通过工作区组合形成上下文链 |
| 项目与接口之间 | 无关联                            | 通过映射文件建立对应关系   |
| AI 入口        | 单个 entry/context-entry.md       | 多项目入口串联             |

## 关键决策汇总

| 决策项         | 结论                                                          |
| -------------- | ------------------------------------------------------------- |
| 仓体结构       | smart-dev-kit 单仓 + 主项目独立仓                             |
| 工作区关联     | VSCode 多根工作区连接 smart-dev-kit 和主项目                  |
| SDK 引用       | 手动拷贝，结构简单一次成型后很少动                            |
| 上报挂载       | 挂在 axios 实例上，传入实例 + 项目标识                        |
| 存档隔离       | 按 projectId 区分根目录，多项目共用互不干扰                   |
| 服务拉起       | 根目录 Google ZX 脚本，dispatcher 不管服务启停                |
| 调度入口       | dispatcher 只管 AI 入口编排和加载顺序                         |
| 映射生成       | 服务端内部防抖，延迟批量写入，调用方零心智负担                |
| 框架隔离       | 同仓平级目录，互不干扰                                        |
| kit 与组合模式 | 共存，kit 用于新项目搭建，工作区组合用于日常开发              |
| 映射文件标准化 | 接口层内提供格式约束和字段解释                                |
| 入口文件编排   | dispatcher 作为总调度、总入口，统一编排加载顺序               |
| 字段解释生成   | SDK 自动补全 + CLI 强制修复 + AI 反向丰富，不人工填写         |
| 接口可视化     | api-web 独立前端项目，放 smart-dev-kit 独立根目录，可在线部署 |
| api-web 职责   | 接口浏览 + KIT 使用指南 + AI 指令语句 + SDK 对接文档          |

## 总结

多工作区组合开发套件的核心理念：

- **单仓套件 + 独立业务**：smart-dev-kit 单仓包裹接口层、可视化、架构层、总调度，主项目独立仓不受套件影响
- **分层解耦**：接口层、架构层、业务层各司其职，通过映射文件和入口文件串联
- **自动上报 + 自动生成**：SDK 挂载到 HTTP 实例自动上报，服务端防抖落盘，schema 字段解释三级自动生成
- **可组合**：同一 smart-dev-kit 可搭配不同主项目，同一主项目可切换不同框架的架构层
- **AI 上下文增强**：dispatcher 总入口编排三层信息，AI 反向丰富字段说明，获得完整链路上下文
- **跨框架复用**：接口层天然框架无关，按 projectId 隔离，一次维护多框架共用
- **api-web 人面向入口**：日常启动 Fastify + api-web，提供接口浏览、KIT 指南、AI 指令语句、SDK 文档
- **与 kit 共存**：kit.zip 用于新项目初始化，工作区组合用于日常开发

> 本文仅讨论思考理论和架构设计，不涉及实际的代码实现。
