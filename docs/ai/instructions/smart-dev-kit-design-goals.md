# Smart Dev Kit — 设计目标与使命

---

## 一、现实挑战

团队长期面临多重困境，这些困境相互交织，制约着研发效率的持续提升：

| 困境               | 表现                                                                                                                  |
| ------------------ | --------------------------------------------------------------------------------------------------------------------- |
| **规模之困**       | 项目数量多、体量大、历史包袱重，维护成本持续攀升                                                                      |
| **复杂度之困**     | 核心业务流程链路长，关键模块系统复杂度极高，认知门槛陡峭                                                              |
| **人力与单点之困** | 单人多线作战、补丁式开发成为常态；关键知识集中于个人，人员即瓶颈，经验难以沉淀与复制                                  |
| **上下文之困**     | 缺乏长期规划、成体系的上下文架构，员工零散使用 AI，上下文天然不全，导致输出混乱、错误频发、效率低下，结果反复偏离预期 |
| **试错之困**       | 同一项目多人维护，各自与 AI 协作时踩相同的坑、犯相同的错，纠错经验在个人会话里无法共享，AI 反复走弯路                 |
| **落地之困**       | 精心构建了 AI 指令集与工具链，但团队成员习惯旧模式，不愿主动采纳，工具价值无法释放                                    |
| **度量之困**       | 缺乏套件使用数据，无法判断谁在用、用多少、哪里卡住，推广和督促没有抓手                                                |

---

## 二、套件使命

> 套件使命的存在，是为了构建一个 **AI 驱动的自循环开发支撑体系**。

通过整合六大资产，将散落在人脑中的知识持续沉淀到系统中，形成一条自动化的知识闭环。

---

## 三、设计目标

针对上述七大困境，套件确立以下设计目标：

| 目标               | 说明                                                                 | 应对困境                   |
| ------------------ | -------------------------------------------------------------------- | -------------------------- |
| **上下文体系化**   | 构建分层、可检索的上下文架构，让 AI 每次都能拿到完整且精准的项目信息 | 上下文之困                 |
| **知识自动化沉淀** | 接口数据、字段语义、代码映射自动采集与更新，不依赖人工维护           | 复杂度之困、人力与单点之困 |
| **经验团队共享**   | 纠错记录、避坑经验按项目累积，一人踩坑全团队受益                     | 试错之困                   |
| **低摩擦采纳**     | 统一入口、统一指令、统一配置，接入成本趋近于零                       | 落地之困                   |
| **使用可度量**     | 套件采纳率、使用频次、卡点分布实时可见                               | 度量之困                   |
| **规模免疫**       | 新增项目、新增模块时，套件支撑能力自动扩展，边际成本递减             | 规模之困                   |

---

## 四、核心原则

每项原则明确标注其主要应对的困境，确保从使命到落地的逻辑可追溯：

| 原则             | 内涵                                                                                         | 主应对困境                 |
| ---------------- | -------------------------------------------------------------------------------------------- | -------------------------- |
| **知识外化**     | 让接口行为、业务语义、模块关系从人脑流向数据文件，成为可检索、可校验、可进化的资产           | 复杂度之困、人力与单点之困 |
| **闭环自驱**     | 快照采集、描述生成、映射维护、代码检查各环节自动串联，以自动化对冲规模膨胀                   | 规模之困                   |
| **AI 原生**      | 所有资产天然服务于 AI 协作；主动管理上下文，按需加载、分层喂给，让有限窗口装下最有价值的信息 | 上下文之困                 |
| **降低切换**     | 统一入口、统一指令集、统一配置，减少跨工具、跨上下文的精力损耗，降低采纳门槛                 | 落地之困                   |
| **可度量落地**   | 采集套件使用情况，让采纳率、使用频次、卡点可见可查，为推广和督促提供数据支撑                 | 度量之困                   |
| **错误经验复用** | 按项目累积 AI 协作中的纠错记录与避坑经验，让一个人踩过的坑成为全团队的护栏                   | 试错之困                   |

---

## 五、六大资产

套件围绕六类核心资产构建完整的数据链路：

| 资产                         | 说明                                                                                                                        | 在闭环中的角色      |
| ---------------------------- | --------------------------------------------------------------------------------------------------------------------------- | ------------------- |
| **API 快照数据**             | 接口请求与响应的原始 JSON 存档，按项目 / 模块 / 通道隔离存储，是全部后续资产的数据源头                                      | 闭环起点 — 采集     |
| **接口描述（Schema）**       | 基于快照自动生成的字段说明文件，每个字段标注类型、是否必填、业务含义，将原始数据转化为可读的知识                            | 闭环中枢 — 描述     |
| **代码映射（Mapping）**      | 接口字段与数据库表、TypeScript 类型、前端组件的关联关系，存储于 Schema 内 `mappings` 字段，让 AI 能从接口一路追踪到代码实现 | 闭环桥梁 — 映射     |
| **采集 SDK**                 | 嵌入商业项目的轻量探针，自动拦截 API 请求并上报快照，零人工干预完成数据采集                                                 | 闭环驱动 — 采集     |
| **架构模板（Instructions）** | 按框架（Vue / React / Flutter）组织的编码范式与约束规则，指导 AI 按统一标准生成代码                                         | 闭环规范 — 检查     |
| **管理服务**                 | Fastify 本地服务 + Web 可视化界面，提供存档查询、Schema 浏览、变更对比、使用指南等统一入口                                  | 闭环基座 — 串联全局 |

---

## 六、闭环五环节

知识在系统中沿五个环节持续流转，每个环节有明确的输入与产出：

```
采集 → 描述 → 映射 → 检查 → 进化
```

| 环节     | 做什么                                                                                                                 | 输入                      | 产出                        |
| -------- | ---------------------------------------------------------------------------------------------------------------------- | ------------------------- | --------------------------- |
| **采集** | SDK 自动拦截 API 请求，将原始请求 / 响应上报至服务端存档                                                               | 运行时 API 流量           | 结构化存档文件              |
| **描述** | 基于存档自动生成 Schema，标注字段类型与是否必填，AI 补充业务语义说明                                                   | 存档数据                  | Schema 字段解释文件         |
| **映射** | 建立接口字段与数据库表、TS 类型、前端组件的关联关系                                                                    | Schema + 项目源码         | Schema 内 mappings 字段     |
| **检查** | AI 编码时加载 Schema 与 Mapping，按架构模板校验输出是否符合规范                                                        | Schema + Mapping + 指令集 | 合规的代码生成              |
| **进化** | 接口变更随需求排期同步更新 Schema；AI 协作中的纠错记录与避坑经验按项目持续累积，一人踩坑全团队受益，知识随实践同步迭代 | 需求排期 + AI 协作纠错    | 更新后的 Schema；团队经验库 |

---

## 七、终极衡量

> 解放精力，减少重复劳动与上下文切换 —— 让人专注于创造，而非维护。

核心度量指标：

| 指标              | 目标                                                        | 度量方式                              |
| ----------------- | ----------------------------------------------------------- | ------------------------------------- |
| **AI 输出准确率** | 接口字段、类型、业务语义一次生成正确，减少反复纠错          | Schema 覆盖的接口字段 vs 人工修正次数 |
| **上下文覆盖率**  | 核心接口 100% 有 Schema 描述，关键模块 100% 有 Mapping 关联 | 有 Schema 的接口数 / 总接口数         |
| **套件采纳率**    | 团队全员日常使用，而非个别尝鲜                              | 周活跃项目数 / 总接入项目数           |
| **知识沉淀率**    | 每次纠错记录自动归集到项目经验库，不随会话消失              | 纠错记录条数 / 项目数                 |
| **人均维护耗时**  | 同等规模需求，AI 辅助后人工介入时间显著下降                 | 需求交付周期对比（接入前 vs 接入后）  |

## 八、边界界定

### 它不是

- **不是项目管理工具** — 不跟踪任务进度、不管理排期，不替代 Jira / Linear
- **不是代码生成器** — 不直接产出业务代码，而是为 AI 编码提供精准的上下文与约束
- **不是 API 测试平台** — 不做接口调试、压力测试，不替代 Postman / YAPI 的测试功能
- **不是监控告警平台** — 不关注线上异常与性能指标，不替代 Sentry / Prometheus

### 它是

- **AI 协作的上下文基础设施** — 让 AI 在每次对话中都能拿到完整、准确、结构化的项目知识
- **团队知识的沉淀容器** — 将个人经验转化为可检索、可共享、可进化的团队资产
- **研发规范的执行载体** — 通过指令集与约束规则，让规范不依赖人记忆，而是由系统保障
