# ES2025/2026 新特性与现代 Web APIs [P6-P7]

> 2025-2026 年，JavaScript 语言层面迎来了 Temporal API、Decorators、Iterator Helpers 等重大特性；浏览器平台则新增了 View Transitions API、Scroll-driven Animations、Popover API 等革命性 Web APIs。这些是 2026 面试高频考点。

## 核心概念（What）

### 语言层面（ES2025/2026）

| 特性                      | 状态              | 解决的问题                                |
| ------------------------- | ----------------- | ----------------------------------------- |
| **Temporal API**          | Stage 3/4         | 替代 Date 的现代日期时间 API              |
| **Decorators**            | Stage 3（已实现） | 标准化的装饰器（与 TS 协调）              |
| **Iterator Helpers**      | ES2025            | 迭代器链式操作（map/filter/reduce）       |
| **Promise.withResolvers** | ES2024            | 简化 Promise 外部控制                     |
| **Set Methods**           | ES2025            | 集合运算（union/intersection/difference） |
| **Array.fromAsync**       | ES2024            | 异步迭代器转数组                          |
| **RegExp v flag**         | ES2024            | Unicode 集类字符匹配                      |

### 平台层面（Web APIs 2025/2026）

| API                          | 解决的问题              | 浏览器支持  |
| ---------------------------- | ----------------------- | ----------- |
| **View Transitions API**     | 页面/组件切换动画       | Chrome 111+ |
| **Scroll-driven Animations** | 纯 CSS 滚动驱动动画     | Chrome 115+ |
| **Popover API**              | 原生弹出层管理          | Chrome 114+ |
| **CSS Anchor Positioning**   | CSS 锚点定位（替代 JS） | Chrome 125+ |
| **Navigation API**           | 现代 SPA 路由管理       | Chrome 118+ |
| **CSS Nesting**              | 原生 CSS 嵌套           | 全浏览器    |

## 底层原理（Why）

### 1. Temporal API 的时间模型设计

Temporal 的底层不是「更好的 Date」，而是**三种独立时间模型的严格分离**，解决 Date 对象的根本设计缺陷。

```
Temporal 时间模型：

  Date 的根本缺陷：
    ├── 内部存储：UTC 毫秒数（自 1970-01-01T00:00:00Z）
    ├── 显示时自动转换本地时区（不可控）
    ├── 月份从 0 开始（反直觉）
    └── 可变对象（修改一个引用影响所有引用）

  Temporal 的三种时间类型：
    ├── Instant（时间点）：
    │   ├── 内部存储：UTC 纳秒数（比 Date 精度更高）
    │   ├── 与平台无关（纯数学时间轴上的一个点）
    │   └── 用于：时间戳、计时、跨时区比较
    ├── PlainDate / PlainTime / PlainDateTime（日历时间）：
    │   ├── 只包含“年月日”或“时分秒”，不包含时区
    │   ├── 用于：生日、节日、闹钟（与时区无关的场景）
    │   └── 不能与 Instant 直接比较（缺少时区信息）
    └── ZonedDateTime（完整时间）：
        ├── = Instant + 时区 + 日历
        ├── 可以精确转换为任何时区的显示
        └── 用于：事件时间、会议时间、航班时间

  时区转换算法：
    ZonedDateTime → Instant：
      1. 根据日历提取本地时间分量
      2. 查询 IANA 时区数据库（获取该日期的 UTC 偏移）
      3. 本地时间 - UTC 偏移 = Instant
    Instant → ZonedDateTime（不同时区）：
      1. 从 Instant 获取 UTC 时间
      2. 查询目标时区的 UTC 偏移
      3. UTC + 偏移 = 目标本地时间

  为什么需要严格分离：
    ├── "2026-09-10" 是 PlainDate（生日，与时区无关）
    ├── "2026-09-10T14:00:00+08:00" 是 ZonedDateTime（会议，需要时区）
    └── 混淆两者是 Date 对象所有 bug 的根源
```

### 2. View Transition 的快照 + 动画协议

View Transition 的底层不是「CSS 动画」，而是**截图快照 + DOM 替换 + 动画合成的三阶段协议**。

```
View Transition 执行流程：

  Phase 1: 快照（旧状态）
    ├── 浏览器对当前 DOM 状态截图（生成位图）
    ├── 截图放入 ::view-transition-old 伪元素
    └── 同时暂停所有 CSS 动画和过渡

  Phase 2: DOM 更新
    ├── 执行 JavaScript 回调中的 DOM 操作
    ├── 浏览器计算新 DOM 的布局
    └── 新 DOM 截图放入 ::view-transition-new 伪元素

  Phase 3: 动画合成
    ├── old 和 new 伪元素叠加显示
    ├── 通过 CSS 动画控制过渡效果
    ├── 动画完成后移除伪元素，显示真实 DOM
    └── 整个过程中用户看到的是伪元素，不是真实 DOM

  关键设计：
    ├── 快照是位图（不是 DOM 克隆），性能开销小
    ├── 动画完全由 CSS 控制（开发者自定义过渡效果）
    ├── 命名视图过渡：view-transition-name 属性
    │   ├── 同名元素在旧/新状态间自动匹配
    │   └── 匹配成功 → 元素级别过渡（位置/大小/透明度）
    │   └── 匹配失败 → 淡入淡出
    └── 不支持的浏览器自动降级为无动画（不报错）
```

### 3. Scroll-driven Animation 的时间线绑定机制

Scroll-driven Animation 的底层不是「监听 scroll 事件」，而是**将动画进度绑定到滚动时间线的原生机制**。

```
Scroll-driven Animation 原理：

  传统方案的问题：
    ├── scroll 事件 + requestAnimationFrame
    ├── 每帧执行 JS → 计算进度 → 修改样式
    └── 问题：JS 执行在主线程，与渲染竞争，导致卡顿

  原生方案的核心创新：
    ├── 动画进度不再由时间驱动，而是由滚动位置驱动
    ├── 浏览器合成层直接处理（不经过主线程 JS）
    └── 性能：零 JS 开销，与浏览器渲染管线同步

  两种时间线：
    ├── scroll() 时间线：
    │   ├── 进度 = 元素的 scrollTop / (scrollHeight - clientHeight)
    │   ├── 0% = 滚动到顶部，100% = 滚动到底部
    │   └── 用于：进度条、视差滚动
    └── view() 时间线：
        ├── 进度 = 元素在视口中的可见比例
        ├── entry 0% = 元素刚进入视口
        ├── entry 100% = 元素完全进入视口
        ├── exit 0% = 元素开始离开视口
        └── exit 100% = 元素完全离开视口
        └── 用于：元素进入视口时的动画

  animation-range 控制：
    ├── 指定动画在时间线的哪个范围生效
    ├── entry 0% entry 100% → 元素从进入到完全可见
    ├── cover 0% cover 100% → 元素从进入到完全离开
    └── 精确控制动画的触发时机和持续时间
```

### 4. Popover API 的 Top Layer 堆叠模型

Popover 的底层不是「显示/隐藏 div」，而是**浏览器原生的 Top Layer 堆叠上下文管理**。

```
Top Layer 堆叠模型：

  传统弹窗的问题：
    ├── z-index 战争（每个层都要比上一个更高）
    ├── 焦点管理混乱（Tab 键可以跳出弹窗）
    ├── 点击外部需要手动监听事件关闭
    └── 键盘导航（Escape 关闭）需要手动实现

  Top Layer 解决方案：
    ├── 浏览器维护一个独立的“顶层”（在所有 z-index 之上）
    ├── popover 打开时自动放入 Top Layer
    │   ├── 自动获得最高堆叠顺序（无需 z-index）
    │   ├── 自动管理焦点（打开时聚焦，关闭时返回）
    │   ├── 自动处理 Escape 键关闭
    │   └── 自动处理点击外部关闭（light dismiss）
    └── 多个 popover 按打开顺序堆叠（后进先出）

  堆叠上下文行为：
    ├── popover 创建新的堆叠上下文（内部 z-index 独立）
    ├── 嵌套 popover：子 popover 在父 popover 的 Top Layer 之上
    └── ::backdrop 伪元素：popover 背后的半透明遮罩
```

## 高频面试题

### Q1: Temporal API 解决了 Date 的哪些问题？

**参考答案要点**：

- 时区处理混乱（Date 默认 UTC，显示本地时间）

### Q2: View Transitions API 的工作原理？

**参考答案要点**：

- 浏览器对旧 DOM 状态截图（生成位图）
- 执行 DOM 更新后对新状态截图
- 通过 CSS 伪元素 ::view-transition-old/new 控制过渡动画
- 命名视图过渡（view-transition-name）实现元素级匹配和动画
- 不支持的浏览器自动降级为无动画

### Q3: Scroll-driven Animations 相比 IntersectionObserver 的优势？

**参考答案要点**：

- 动画进度由滚动位置驱动，不依赖 JS 计算
- 浏览器合成层直接处理，零主线程开销
- scroll() 时间线（页面滚动进度）和 view() 时间线（元素可见比例）
- animation-range 精确控制动画触发时机
- 纯 CSS 实现，无需 IntersectionObserver + requestAnimationFrame
