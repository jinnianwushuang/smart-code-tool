# 实时协作系统设计 [P8]

> 实时协作是前端架构中最具挑战性的系统设计之一。2026 年，CRDT 成为主流方案，结合 WebSocket/WebTransport 实现毫秒级同步。

## 核心概念（What）

### 实时协作核心技术

```
┌─────────────────────────────────┐
│         协作应用层               │
│  文档编辑 │ 白板 │ 表格 │ 设计   │
├─────────────────────────────────┤
│         冲突解决层               │
│  CRDT │ OT │ 最后写入者胜出     │
├─────────────────────────────────┤
│         通信层                   │
│  WebSocket │ WebTransport │ SSE │
├─────────────────────────────────┤
│         存储层                   │
│  操作日志 │ 快照 │ 版本历史      │
└─────────────────────────────────┘
```

### CRDT vs OT

| 特性       | CRDT               | OT                |
| ---------- | ------------------ | ----------------- |
| 冲突解决   | 数据结构保证收敛   | 中心服务器转换    |
| 去中心化   | ✓（P2P 可用）      | ✗（需要中心节点） |
| 离线支持   | 天然支持           | 需要额外处理      |
| 实现复杂度 | 高（数据结构复杂） | 中（算法复杂）    |
| 代表实现   | Yjs, Automerge     | Google Docs       |

## 底层原理（Why）

### 1. CRDT 数据结构原理

CRDT 的核心不是「用 Yjs 库」，而是通过**特定的数据结构设计**保证分布式合并的收敛性（最终一致性）。

```
CRDT 核心数据结构：

  RGA（Replicated Growable Array）—— 有序序列 CRDT：
    ├── 每个字符/元素分配一个全局唯一的 ID（siteId + counter）
    ├── 元素之间通过“相对位置”引用（不是绝对索引）
    │   ├── 插入时：记录“我插在哪个元素后面”
    │   └── 删除时：标记为墓碑（tombstone），不物理删除
    ├── 合并算法：
    │   ├── 两个副本各自独立插入
    │   ├── 合并时按 ID 的全序关系排序
    │   └── 相同位置插入时：ID 大的优先（保证确定性）
    └── 为什么能收敛：
        ├── 插入操作是交换的（A 后 B = B 后 A，按 ID 排序确定）
        ├── 删除操作是幂等的（删多次 = 删一次）
        └── 操作顺序不影响最终结果

  Yjs 的相对位置算法（Y Relative Position）：
    ├── 不用绝对索引（因为插入/删除会导致索引偏移）
    ├── 用“锚点”定位：
    │   ├── 找到目标元素的前一个元素（按 ID 匹配）
    │   └── 记录“在该元素之后的第 N 个位置”
    ├── 即使文档被其他人修改，锚点仍然有效
    └── 时间复杂度：O(log N)（二分查找锚点）

  其他 CRDT 类型：
    ├── G-Counter（Grow-only Counter）：每个节点独立计数，合并取最大值
    ├── PN-Counter（正负计数器）：两个 G-Counter，一个加一个减
    ├── YMap（可复制 Map）：每个 key 对应一个 LWW-Register
    └── LWW-Register（最后写入者胜出）：每个值带时间戳，合并取最新
```

### 2. Awareness 协议与光标同步

实时协作中光标/选区同步不是「广播位置」，而是一个独立的**临时状态广播协议**。

```
Awareness 协议（Yjs 实现）：

  与文档状态的区别：
    ├── 文档状态（Y.Doc）：永久、合并、CRDT 保证收敛
    └── Awareness 状态：临时、不合并、不持久化、仅在线时存在

  工作原理：
    1. 每个客户端维护一个本地 Awareness 对象：
       { user: { name, color }, cursor: { anchor, head } }
    2. 本地状态变更时（光标移动）：
       ├── 更新本地 Awareness
       ├── 广播给所有连接的客户端
       └── 消息类型：{ type: 'awareness', updates: [...] }
    3. 接收其他客户端的 Awareness 更新：
       ├── 更新远程用户状态表（Map<clientId, Awareness>）
       ├── 触发 UI 更新（渲染远程光标）
       └── 设置超时计时器（30s 无更新 → 认为离线 → 移除光标）
    4. 心跳机制：
       ├── 每 15s 发送一次 Awareness 更新（即使光标未移动）
       └── 保证在线状态及时刷新

  光标渲染优化：
    ├── 远程光标用绝对定位（不干扰本地编辑）
    ├── 光标移动用 CSS transition（平滑动画，隐藏网络延迟）
    ├── 选区高亮用半透明覆盖层
    └── 用户头像显示在光标旁边（颜色与光标一致）
```

### 3. 增量同步与状态向量算法

CRDT 的同步不是「发送全部数据」，而是基于**状态向量（State Vector）的增量差异同步**。

```
状态向量同步协议：

  状态向量（State Vector）：
    ├── 每个客户端维护一个 Map<clientId, counter>
    ├── 记录“我已经收到了每个客户端的第几个操作”
    └── 例：{ clientA: 5, clientB: 3 } 表示已处理 A 的 5 个操作和 B 的 3 个

  增量同步流程：
    1. 客户端 A 连接服务端
    2. A 发送自己的 StateVector 给服务端
    3. 服务端对比 A 的 StateVector 和自己的 StateVector：
       ├── 找出 A 缺失的操作（服务端有但 A 没有的）
       ├── 编码为 Update 消息
       └── 发送给 A
    4. A 应用缺失的操作 → 文档追上最新状态
    5. 后续操作实时广播（增量）

  编码优化（Yjs 的 Update 编码）：
    ├── 操作按 clientId 分组
    ├── 每个客户端的操作按 counter 排序
    ├── 使用差分编码（只存偏移量，不存绝对值）
    ├── 使用 VarInt 压缩（小数字用 1 字节，大数字用多字节）
    └── 典型压缩率：原始 JSON 的 1/10 ~ 1/50

  快照压缩（定期截断操作日志）：
    ├── 操作日志无限增长 → 同步变慢
    ├── 定期生成快照（文档当前状态的序列化）
    ├── 同步时：先加载快照，再应用快照之后的操作
    └── 快照频率：每 100 个操作 或 每 5 分钟
```

### 4. WebSocket 通信层的背压控制与断线重连

实时协作的通信层不是「WebSocket 发数据」，而是需要解决**背压、重连、消息有序性**问题。

```
WebSocket 通信层设计：

  背压控制（Backpressure）：
    ├── 问题：用户快速输入时，操作产生速度 > 网络发送速度
    ├── 方案 1：操作合并（Debouncing）
    │   ├── 50ms 内的多个操作合并为一个 Update
    │   └── 减少消息数，但增加延迟
    ├── 方案 2：队列 + 限速
    │   ├── 操作进入发送队列
    │   └── 按固定速率发送（如每 16ms 一帧）
    └── 方案 3：WebSocket 缓冲监控
        ├── 检查 ws.bufferedAmount
        └── 缓冲区满时暂停发送，等待 drain 事件

  断线重连协议：
    1. 检测断线：WebSocket close 事件 / 心跳超时
    2. 重连策略：指数退避（1s → 2s → 4s → 8s → 最大 30s）
    3. 重连后同步：
       ├── 发送本地 StateVector
       ├── 服务端返回缺失的操作
       ├── 本地应用缺失操作 → 追上最新状态
       └── 本地未发送的操作重新发送
    4. 离线期间：
       ├── 操作继续记录在本地（Yjs 支持离线编辑）
       ├── UI 显示“离线”状态
       └── 重连后自动合并

  消息有序性保证：
    ├── WebSocket 本身保证同一连接内消息有序
    ├── 但重连后可能乱序 → 用 counter 排序
    ├── 每个操作带 (clientId, counter) → 接收端按序应用
    └── 乱序到达时缓存，等待缺失的操作到达后再应用
```

## 高频面试题

### Q1: CRDT 和 OT 如何选择？

**参考答案要点**：

- CRDT：去中心化、离线支持好、P2P 可用
- OT：实现相对简单、Google Docs 验证
- 新项目推荐 CRDT（Yjs/Automerge）
- 选择依据：是否需要离线、是否需要 P2P、团队经验

### Q2: 如何保证实时协作的延迟体验？

**参考答案要点**：

- 本地优先（先更新本地 UI，再同步）
- 操作预测（乐观更新）
- WebSocket 长连接
- 操作合并（批量发送）
- 目标：感知延迟 < 100ms

### Q3: 如何处理大文档的协作性能？

**参考答案要点**：

- 分段加载（只加载可视区域）
- 定期快照（压缩操作日志）
- 增量同步（只发送差异）
- 虚拟滚动（大列表/大表格）
- 懒加载（按需加载内容块）
