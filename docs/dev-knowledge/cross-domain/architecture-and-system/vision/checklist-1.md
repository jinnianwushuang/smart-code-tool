# 顶级大前端架构师日常自检复盘清单

在超一线科技公司，架构师的核心价值在于通过工程手段将"混沌"变为"有序"。本清单提供一个多维度的自检框架，帮助架构师审视系统现状并预判潜在风险。

## 一、每日必看：运行监控与稳定性 (5-10 min)

### 1.1 稳定性看板

| 检查项      | 工具           | 告警阈值       | 处理优先级    |
| ----------- | -------------- | -------------- | ------------- |
| JS Error 率 | Sentry         | > 0.1% 突增    | P0 - 立即处理 |
| Top 5 错误  | Sentry Issues  | 新增未分类错误 | P1 - 当日处理 |
| API 成功率  | Grafana        | < 99.5%        | P0 - 立即处理 |
| 页面可用性  | Uptime Monitor | < 99.9%        | P0 - 立即处理 |

### 1.2 核心性能指标

| 指标         | 达标线     | 预警线     | 数据源           |
| ------------ | ---------- | ---------- | ---------------- |
| LCP (P75)    | < 2.5s     | > 3.0s     | RUM (web-vitals) |
| INP (P75)    | < 200ms    | > 300ms    | RUM (web-vitals) |
| CLS (P75)    | < 0.1      | > 0.15     | RUM (web-vitals) |
| TTFB (P75)   | < 800ms    | > 1.2s     | RUM / CDN 日志   |
| 首屏 JS 体积 | < 200KB gz | > 250KB gz | Bundle Analysis  |

### 1.3 构建流水线

| 检查项       | 正常范围   | 异常处理                       |
| ------------ | ---------- | ------------------------------ |
| CI 成功率    | > 98%      | 排查失败原因，是否基础设施问题 |
| 平均构建时间 | < 5min     | 检查缓存命中率，是否依赖冲突   |
| 部署频率     | 每日 1+ 次 | 是否有阻塞发布的 Bug           |
| 回滚次数     | 0 次/周    | 分析回滚原因，加强发布前检查   |

## 二、每周复盘：工程提效与治理 (1-2 h)

### 2.1 研发效能审计

| 指标           | 目标值  | 测量方式        | 改进手段         |
| -------------- | ------- | --------------- | ---------------- |
| 本地冷启动     | < 20s   | 团队抽样调查    | Rspack/Vite 优化 |
| HMR 响应       | < 500ms | 开发者反馈      | 减少全量刷新     |
| 远程缓存命中率 | > 80%   | Turborepo 统计  | 优化缓存 Key     |
| PR 合并周期    | < 24h   | GitHub Insights | 减少 Review 阻塞 |
| 发布频率       | 每日 1+ | 部署日志        | 简化发布流程     |

### 2.2 组件库治理

```markdown
## 每周组件库检查

- [ ] 本周是否有新的"临时组件"产生？
      → 评估是否可以抽象到设计系统
- [ ] 关键 API 变更是否同步更新了 Storybook？
      → 文档滞后会导致使用错误
- [ ] 组件的 Bundle Size 是否有异常增长？
      → 检查是否引入了不必要的依赖
- [ ] 是否有组件被废弃但未标记 @deprecated？
      → 及时清理，减少维护负担
- [ ] 视觉回归测试 (Chromatic) 是否有未处理的 Diff？
      → 确认是预期变更还是 Bug
```

### 2.3 依赖红线扫描

| 检查项       | 工具             | 频率     | 处理标准       |
| ------------ | ---------------- | -------- | -------------- |
| 高危漏洞     | Snyk / npm audit | 每日自动 | 24h 内修复     |
| 中危漏洞     | Snyk             | 每周     | 本周内修复     |
| 过期依赖     | npm outdated     | 每周     | 评估升级计划   |
| License 合规 | license-checker  | 每月     | 禁止 GPL 混入  |
| 无用依赖     | depcheck         | 每月     | 移除未使用的包 |

### 2.4 代码审计 (High-Level CR)

```markdown
## 每周代码抽检清单

抽检范围：核心模块 + 本周变更量最大的文件

- [ ] 是否存在违背单一职责原则的"上帝组件"？
      → 单文件 > 400 行需要关注
- [ ] 是否有滥用全局状态的情况？
      → 局部状态不应提升到全局
- [ ] 是否有硬编码的魔法数字/字符串？
      → 应提取为常量或配置
- [ ] 是否有未处理的异步错误？
      → 所有 Promise 必须有 catch
- [ ] 是否有潜在的性能问题？
      → 大列表未虚拟化、频繁重渲染、内存泄漏
- [ ] 是否有安全隐患？
      → XSS 风险、敏感信息暴露、不安全的依赖
```

## 自动化检测脚本参考

### 技术债务扫描脚本

```bash
#!/bin/bash
# tech-debt-scan.sh - 每周自动执行

echo "=== 技术债务扫描报告 ==="
echo "日期: $(date +%Y-%m-%d)"
echo ""

# 1. 大文件检测 (> 400 行)
echo "📦 超过 400 行的文件:"
find src -name "*.ts" -o -name "*.tsx" -o -name "*.vue" | \
  xargs wc -l | sort -rn | head -20 | awk '$1 > 400'

# 2. TODO/FIXME 统计
echo ""
echo "📝 TODO/FIXME 数量:"
grep -r "TODO\|FIXME\|HACK\|XXX" src --include="*.ts" --include="*.vue" | wc -l

# 3. any 类型使用
echo ""
echo "⚠️  TypeScript 'any' 使用次数:"
grep -r ": any\|as any" src --include="*.ts" --include="*.tsx" | wc -l

# 4. console.log 残留
echo ""
echo "🔍 console.log 残留:"
grep -r "console\.log" src --include="*.ts" --include="*.vue" | wc -l

# 5. 依赖过期检查
echo ""
echo "📅 过期依赖:"
pnpm outdated --format json 2>/dev/null | jq 'length'

echo ""
echo "=== 扫描完成 ==="
```

### 性能预算检查脚本

```bash
#!/bin/bash
# perf-budget-check.sh - CI 中自动执行

MAX_MAIN_SIZE=204800  # 200KB in bytes
MAX_ROUTE_SIZE=51200  # 50KB in bytes

echo "=== 性能预算检查 ==="

# 检查主 Bundle 大小
MAIN_SIZE=$(stat -f%z dist/assets/index-*.js 2>/dev/null || stat -c%s dist/assets/index-*.js 2>/dev/null)

if [ "$MAIN_SIZE" -gt "$MAX_MAIN_SIZE" ]; then
  echo "❌ 主 Bundle 超出预算: ${MAIN_SIZE}B > ${MAX_MAIN_SIZE}B"
  exit 1
else
  echo "✅ 主 Bundle: ${MAIN_SIZE}B / ${MAX_MAIN_SIZE}B"
fi

# 检查路由级 Bundle
for file in dist/assets/page-*.js; do
  SIZE=$(stat -f%z "$file" 2>/dev/null || stat -c%s "$file" 2>/dev/null)
  if [ "$SIZE" -gt "$MAX_ROUTE_SIZE" ]; then
    echo "❌ 路由 Bundle 超出预算: $file (${SIZE}B)"
    exit 1
  fi
done

echo "✅ 所有路由 Bundle 在预算内"
echo "=== 检查通过 ==="
```

## 工具推荐矩阵

| 类别        | 推荐工具                   | 用途                         | 优先级  |
| ----------- | -------------------------- | ---------------------------- | ------- |
| 错误监控    | Sentry                     | JS 错误追踪 + 性能监控       | P0 必装 |
| 性能监控    | web-vitals + Grafana       | Core Web Vitals 采集与可视化 | P0 必装 |
| 可用性监控  | UptimeRobot / Better Stack | 页面可用性检测               | P0 必装 |
| 安全扫描    | Snyk / Socket.dev          | 依赖漏洞 + 供应链安全        | P0 必装 |
| 代码质量    | SonarQube                  | 技术债务量化                 | P1 推荐 |
| Bundle 分析 | rollup-plugin-visualizer   | 包体积分析                   | P1 推荐 |
| 视觉回归    | Chromatic / Percy          | UI 变更检测                  | P2 可选 |
| 日志分析    | OpenTelemetry + Jaeger     | 全链路追踪                   | P1 推荐 |
| 告警通知    | PagerDuty / 飞书机器人     | 异常即时通知                 | P0 必装 |

---

> **核心总结**：自检不是形式主义，而是架构师对系统健康度的持续感知。好的自检体系应该是：自动化为主（减少人工负担）、数据驱动（避免主观判断）、闭环管理（发现问题必须跟进解决）。
