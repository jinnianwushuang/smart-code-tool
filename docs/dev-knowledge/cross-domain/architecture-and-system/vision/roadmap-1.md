## 第一阶段：向下扎根（底层原理与计算机科学基础）

**目标**：突破"框架使用者"的瓶颈，具备修改底层引擎或自研工具的能力。

**预计时间**：6-12 个月

### 1.1 JavaScript/TypeScript 深度

| 知识点              | 学习深度                          | 验证标准               |
| ------------------- | --------------------------------- | ---------------------- |
| V8 执行机制         | 理解 Ignition/TurboFan 分层编译   | 能解释为什么某段代码慢 |
| 垃圾回收            | 掌握 Scavenge/Mark-Sweep 触发条件 | 能定位内存泄漏         |
| 事件循环            | 理解宏任务/微任务/渲染时机        | 能预测异步代码执行顺序 |
| TypeScript 类型编程 | 掌握条件类型/映射类型/递归类型    | 能实现复杂的类型工具   |
| 原型链与闭包        | 深入理解对象模型和作用域          | 能解释框架响应式原理   |

**学习资源**：

- 《你不知道的 JavaScript》系列（上中下）
- V8 官方博客 (v8.dev/blog)
- TypeScript Handbook + 类型挑战 (type-challenges)

**里程碑检查点**：

- [ ] 能阅读 V8 源码并解释关键函数
- [ ] 完成 type-challenges 中 hard 难度的 20 题
- [ ] 写一篇关于 JS 引擎原理的深度文章

### 1.2 浏览器与运行时

```
浏览器渲染管线（必须精通）：

HTML → DOM Tree
              ↘
               Render Tree → Layout → Paint → Composite → 屏幕
              ↗
CSS  → CSSOM

关键优化点：
├── 减少 Reflow：批量 DOM 操作、避免布局抖动
├── 减少 Repaint：使用 transform/opacity（仅触发 Composite）
├── 层爆炸控制：will-change 不要滥用
└── 关键渲染路径：首屏资源优先级
```

**Node.js/Bun/Deno 运行时**：

- Event Loop 六阶段（timers → pending → poll → check → close）
- Stream 背压（Backpressure）处理
- Worker Threads 多线程模型
- Bun 的 JavaScriptCore vs Node 的 V8 性能差异

### 1.3 WebAssembly

| 场景              | 何时使用                  | 工具链              |
| ----------------- | ------------------------- | ------------------- |
| 计算密集型        | 图片处理、加密、物理引擎  | Rust → wasm-pack    |
| 现有 C/C++ 库移植 | ffmpeg、OpenCV            | Emscripten          |
| 高性能解析        | 代码编辑器、Markdown 解析 | tree-sitter WASM    |
| 边缘计算          | Cloudflare Workers        | Rust/AssemblyScript |

**常见卡点与突破**：

- 卡点：觉得底层原理"没用"，想直接学框架
- 突破：尝试修复一个框架的 Bug，你会发现底层知识是必需的
- 卡点：V8 源码太庞大，不知从何看起
- 突破：从一个小功能（如 `console.log` 的实现）入手，顺藤摸瓜

## 第二阶段：向外扩展（全栈与云原生能力）

**目标**：打破"端"的边界，具备设计全链路闭环系统的能力。

**预计时间**：6-12 个月

### 2.1 全栈架构

| 层级     | 技术栈                        | 掌握程度                 |
| -------- | ----------------------------- | ------------------------ |
| BFF 层   | NestJS / Fastify / Hono       | 能独立设计和实现         |
| 数据库   | PostgreSQL + Prisma / Drizzle | 能设计 Schema + 优化查询 |
| 缓存     | Redis (缓存/会话/队列)        | 理解缓存策略和一致性     |
| 消息队列 | Kafka / Redis Streams         | 理解异步解耦场景         |
| 认证授权 | JWT + OAuth2 + RBAC           | 能设计完整权限体系       |

### 2.2 云原生与 DevOps

```
必须掌握的云原生技能树：

Docker
├── Dockerfile 多阶段构建（减小镜像体积）
├── docker-compose 本地开发环境编排
└── 镜像安全扫描（Trivy/Grype）

Kubernetes (了解即可，不需精通)
├── Pod/Deployment/Service 基本概念
├── Ingress 路由配置
├── HPA 自动扩缩容
└── ConfigMap/Secret 配置管理

CI/CD
├── GitHub Actions / GitLab CI 深度定制
├── 构建缓存策略（依赖缓存 + 产物缓存）
├── 灰度发布 / 蓝绿部署
└── 自动回滚机制

CDN & 边缘
├── CDN 缓存策略（Cache-Control / ETag）
├── 边缘计算（Cloudflare Workers / Vercel Edge）
└── 全球加速（多区域部署）
```

- [ ] 独立完成一个全栈项目的设计、开发、部署
- [ ] 能编写生产级 Dockerfile 和 K8s 配置
- [ ] 设计并实现一套 CI/CD 流水线
- [ ] 理解 CDN 原理，能配置缓存策略

**常见卡点与突破**：

## 第三阶段：工业化交付（极致工程化与架构模式）

**目标**：解决超大型项目的复杂性，建立团队研发的"确定性"。

**预计时间**：1-2 年

### 3.1 Monorepo 与基建

| 能力           | 具体要求                                |
| -------------- | --------------------------------------- |
| pnpm workspace | catalog 协议、overrides、依赖去重       |
| Turborepo/Nx   | 任务编排、远程缓存、affected 策略       |
| 版本管理       | Changesets 语义化发布、CHANGELOG 自动化 |
| 代码共享       | packages/shared 设计、跨应用类型复用    |

### 3.2 构建工具深度

```
构建工具演进路径（必须理解每一代的设计哲学）：

第一代: Grunt/Gulp (2012-2014)
├── 特点：任务流（Task Runner）
├── 局限：手动配置每一步，无模块打包
└── 遗产：自动化思维

第二代: Webpack (2014-2020)
├── 特点：模块打包（Bundler）、Loader/Plugin 生态
├── 局限：配置复杂、构建速度慢（JS 实现）
└── 遗产：模块化思想、Code Splitting

第三代: Vite/esbuild (2020-2023)
├── 特点：ESM 原生、按需编译、Go/Rust 实现
├── 局限：生产构建仍需 Rollup
└── 遗产：开发体验至上

第四代: Rspack/Turbopack/Rolldown (2023-)
├── 特点：Rust 实现、Webpack 兼容、增量计算
├── 方向：统一开发/生产构建引擎
└── 未来：与 Oxc (Rust 工具链) 融合
```

### 3.3 微前端与模块联邦

| 方案              | 原理                  | 适用场景     | 复杂度 |
| ----------------- | --------------------- | ------------ | ------ |
| Module Federation | 运行时模块共享        | 大型应用拆分 | 高     |
| qiankun           | JS 沙箱 + 样式隔离    | 遗留系统迁移 | 中     |
| wujie             | WebComponent + iframe | 强隔离需求   | 中     |
| iframe            | 原生隔离              | 第三方集成   | 低     |
| 构建时集成        | npm 包 + 统一构建     | 单团队多模块 | 低     |

### 3.4 设计系统 (Design System)

```
设计系统三层架构：

Layer 1: Design Tokens（设计变量）
├── 颜色、间距、字体、阴影、动画
├── 工具：Style Dictionary / Figma Variables
└── 输出：CSS Variables / JSON / 各平台代码

Layer 2: Components（组件库）
├── 基础组件：Button, Input, Select, Modal...
├── 业务组件：UserCard, OrderTable, PaymentForm...
├── 工具：Storybook + Chromatic (视觉回归)
└── 文档：API 文档 + 使用示例 + 设计指南

Layer 3: Patterns（设计模式）
├── 页面模板：列表页、详情页、表单页
├── 交互模式：搜索、筛选、分页、批量操作
└── 布局系统：Grid、Flex、响应式断点
```

### 3.5 里程碑检查点

- [ ] 主导过 50+ 包的 Monorepo 治理
- [ ] 能从零搭建一套 CI/CD + 构建 + 发布流水线
- [ ] 设计并落地过微前端方案
- [ ] 推动过设计系统从 0 到 1 建设

## 第四阶段：科学治理（性能、安全与质量红线）

**目标**：建立数据驱动的评价体系，为生产环境提供屏障。

**预计时间**：1-2 年

### 4.1 性能治理

| 维度     | 指标                 | 工具                    | 达标线         |
| -------- | -------------------- | ----------------------- | -------------- |
| 加载性能 | LCP, FCP, TTFB       | web-vitals + RUM        | LCP < 2.5s     |
| 交互性能 | INP, TBT, Long Tasks | Performance API         | INP < 200ms    |
| 视觉稳定 | CLS                  | Layout Shift API        | CLS < 0.1      |
| 资源体积 | Bundle Size          | size-limit / bundlesize | 增量 < 10KB/PR |
| 运行时   | FPS, Memory          | DevTools Profiler       | FPS > 55       |

### 4.2 安全保障

```
前端安全防线（纵深防御）：

Layer 1: 编码阶段
├── ESLint security rules
├── 禁止 dangerouslySetInnerHTML / v-html
└── 依赖审计 (npm audit / Snyk)

Layer 2: 构建阶段
├── CSP (Content Security Policy) 配置
├── Subresource Integrity (SRI)
└── 环境变量隔离（不泄露 Secret）

Layer 3: 运行时
├── XSS 防御（输出编码 + CSP）
├── CSRF 防御（SameSite Cookie + Token）
├── 点击劫持防御（X-Frame-Options）
└── 敏感数据脱敏（前端不存储密码/Token 明文）

Layer 4: 监控阶段
├── 异常行为检测（大量 404/403）
├── 依赖包变更告警
└── 安全事件响应流程
```

### 4.3 自动化测试

| 测试类型 | 工具                 | 覆盖目标       | 执行时机 |
| -------- | -------------------- | -------------- | -------- |
| 单元测试 | Vitest / Jest        | 核心逻辑 > 80% | 每次提交 |
| 组件测试 | Testing Library      | 关键组件 100%  | 每次提交 |
| E2E 测试 | Playwright / Cypress | 核心流程 100%  | 每次合并 |
| 视觉回归 | Chromatic / Percy    | UI 组件 100%   | 每次 PR  |
| 性能测试 | Lighthouse CI        | 核心页面       | 每次部署 |
| 安全扫描 | Snyk / OWASP ZAP     | 全部依赖       | 每日     |

### 4.4 里程碑检查点

- [ ] 建立过完整的性能监控体系（采集→分析→告警→优化）
- [ ] 主导过安全漏洞修复和防御体系建设
- [ ] 设计过测试策略并推动团队落地
- [ ] 能用数据证明质量改进的效果

## 第五阶段：决策与影响力（架构决策与技术洞察）

**目标**：在混沌中建立秩序，引领团队的技术走向。

**预计时间**：2-3 年

### 5.1 架构决策体系

| 工具     | 用途                 | 频率         |
| -------- | -------------------- | ------------ |
| RFC      | 重大变更前的意见征求 | 每月 1-2 份  |
| ADR      | 记录决策的背景和权衡 | 每个重要决策 |
| 技术雷达 | 评估新技术的成熟度   | 每季度更新   |
| 架构评审 | 新项目的架构把关     | 每个新项目   |

### 5.2 ROI 评估能力

```
技术投入评估框架：

输入：
├── 开发成本（人天 × 单价）
├── 维护成本（长期运维投入）
├── 迁移成本（数据迁移 + 兼容层）
└── 机会成本（不做这件事能做什么）

输出：
├── 效率收益（节省的人时 × 单价）
├── 质量收益（故障减少 × 单次损失）
├── 体验收益（性能提升 → 转化率提升 → GMV）
└── 战略收益（技术壁垒、人才吸引）

决策规则：
├── ROI > 3x 且回收期 < 6个月 → 立即执行
├── ROI 1-3x 或回收期 6-12个月 → 排期执行
├── ROI < 1x 但有战略价值 → 小规模试点
└── ROI < 1x 且无战略价值 → 放弃
```

### 5.3 里程碑检查点

- [ ] 建立并运营过 ADR/RFC 制度
- [ ] 主导过公司级技术战略决策
- [ ] 能用商业语言向 CTO/VP 汇报技术价值
- [ ] 培养过能独当一面的架构师
