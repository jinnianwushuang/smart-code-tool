# 前端编程的终极朴素思想：数据 · 算法 · 显示 三者分离

> 前端编程千变万化，框架层出不穷，但剥去所有抽象层之后，剩下的只有一个最朴素的思想：**把接口原始数据、算法处理、界面显示数据三者彻底分离**。这不是某种设计模式的发明，而是对浏览器本身架构的回归——浏览器就是这么设计的，前端代码只是在与它同构。

---

## 一、思想的核心：三层分离

### 1.1 三层定义

```
┌─────────────────────────────────────────────────────────────┐
│                                                             │
│   ① 接口原始数据（Raw Data）                                 │
│      来自后端 API 的原始响应，未经任何加工                     │
│      特征：结构由后端决定，字段命名、嵌套层级、数据格式不可控    │
│                                                             │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│   ② 算法（Algorithm / Transform）                           │
│      对原始数据进行加工、计算、转换的纯逻辑                    │
│      特征：不依赖 DOM，不依赖框架，输入确定则输出确定           │
│                                                             │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│   ③ 界面显示数据（View Model / Display Data）                │
│      直接驱动 UI 渲染的数据结构                               │
│      特征：结构由界面决定，与组件树一一对应，框架感知           │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 1.2 一句话概括

```
接口原始数据 → [算法] → 界面显示数据 → [框架渲染] → 用户看到的界面
```

**中间不存任何"既不是原始数据、也不是显示数据、又不得不存在"的模糊状态。**

### 1.3 为什么叫"终极最朴素"

- **终极**：无论技术栈怎么演进（jQuery → Angular → React → Vue → Svelte），这三层永远存在，无法消灭，只能重组。
- **朴素**：不需要任何框架支持，不依赖任何设计模式，用最简单的变量赋值就能表达。
- **分离**：三者的边界清晰，职责单一，互不渗透。

## 二、反模式：三者耦合的代价

### 2.1 典型耦合场景

```javascript
// ❌ 反模式：在组件中直接处理接口数据并渲染
async function loadUserList() {
  const res = await fetch('/api/users')
  const data = await res.json()

  // 直接在组件状态里混合了原始数据和展示逻辑
  userList.value = data.list
    .filter((u) => u.status === 1)
    .map((u) => ({
      ...u, // 原始数据被原封不动带入视图层
      displayName: `${u.first_name} ${u.last_name}`,
      avatarUrl: u.avatar || '/default.png',
      lastLoginText: dayjs(u.last_login_at).fromNow(),
    }))
    .sort((a, b) => b.score - a.score)
}
```

**问题在哪？**

| 问题               | 说明                                                            |
| ------------------ | --------------------------------------------------------------- |
| 原始数据污染视图层 | `...u` 把后端所有字段都带进了组件，视图层持有了大量不需要的数据 |
| 算法无处安放       | 过滤、排序、格式化逻辑散落在组件函数里，无法独立测试            |
| 不可复用           | 换一个页面需要同样的用户列表？复制粘贴                          |
| 不可测试           | 算法和 DOM/框架耦合，无法脱离浏览器环境单独跑                   |

### 2.2 分离后的写法

```javascript
// ✅ ① 接口原始数据层 —— 只管拿数据
async function fetchUsers() {
  const res = await fetch('/api/users')
  return res.json() // 返回原始数据，不做任何加工
}

// ✅ ② 算法层 —— 纯函数，不依赖任何框架和 DOM
function buildUserViewModel(rawData) {
  return rawData.list
    .filter((u) => u.status === 1)
    .sort((a, b) => b.score - a.score)
    .map((u) => ({
      id: u.id,
      displayName: `${u.first_name} ${u.last_name}`,
      avatarUrl: u.avatar || '/default.png',
      lastLoginText: dayjs(u.last_login_at).fromNow(),
    }))
}

// ✅ ③ 界面显示层 —— 只管把 ViewModel 交给模板
const users = ref([])

async function loadUsers() {
  const rawData = await fetchUsers() // 拿原始数据
  users.value = buildUserViewModel(rawData) // 算法转换 → 显示数据
}
```

三层各司其职，边界清晰。

## 三、这种思想为什么是"对"的——浏览器架构的启示

前端代码最终运行在浏览器中。**浏览器的内部架构，恰好就是这种三层分离的终极实现。** 前端代码的三层分离，本质上是在与浏览器的设计同构。

### 3.1 浏览器的核心管线

```
┌────────────────────────────────────────────────────────────────────┐
│                        浏览器内部架构                               │
│                                                                    │
│  ① 数据获取层                                                      │
│  ┌──────────────────────────────────────────────────┐              │
│  │  Network Stack（网络栈）                          │              │
│  │  • HTTP 请求/响应                                 │              │
│  │  • HTML 字节流 → 原始 token 流                    │              │
│  │  • 资源加载（CSS、JS、图片、字体）                 │              │
│  │                                                   │              │
│  │  特征：只负责"拿到原始数据"，不理解内容含义        │              │
│  └──────────────────────────────────────────────────┘              │
│                          ↓                                         │
│  ② 算法处理层                                                      │
│  ┌──────────────────────────────────────────────────┐              │
│  │  Rendering Engine（渲染引擎）                      │              │
│  │  • HTML Parser → DOM Tree                         │              │
│  │  • CSS Parser → CSSOM Tree                        │              │
│  │  • DOM + CSSOM → Render Tree（布局计算）           │              │
│  │  • Layout / Reflow：计算每个节点的几何信息         │              │
│  │                                                   │              │
│  │  JS Engine（JavaScript 引擎）                      │              │
│  │  • 解析执行 JS 代码                               │              │
│  │  • 数据计算、逻辑处理、状态管理                    │              │
│  │                                                   │              │
│  │  特征：纯粹的"计算与转换"，输入确定则输出确定      │              │
│  └──────────────────────────────────────────────────┘              │
│                          ↓                                         │
│  ③ 界面显示层                                                      │
│  ┌──────────────────────────────────────────────────┐              │
│  │  Compositor & Painter（合成与绘制）                │              │
│  │  • Paint：将 Render Tree 转化为绘制指令            │              │
│  │  • Rasterize：将绘制指令光栅化为像素               │              │
│  │  • Composite：分层合成，输出最终帧                 │              │
│  │  • GPU Acceleration：GPU 合成图层                 │              │
│  │                                                   │              │
│  │  特征：只关心"最终怎么画到屏幕上"                  │              │
│  └──────────────────────────────────────────────────┘              │
│                          ↓                                         │
│                     用户看到的像素                                    │
└────────────────────────────────────────────────────────────────────┘
```

### 3.2 前端三层 vs 浏览器三层：同构映射

```
┌─────────────────────────────────────────────────────────────────┐
│                     同构关系                                      │
│                                                                  │
│   前端代码                    浏览器内部                          │
│   ─────────                   ──────────                          │
│   ① 接口原始数据       ↔      Network Stack（网络栈）            │
│      "拿到什么就是什么"        "收到什么字节就是什么字节"          │
│                                                                  │
│   ② 算法/转换逻辑     ↔      Rendering Engine + JS Engine       │
│      "纯计算，不关心显示"      "解析、计算布局，纯逻辑处理"       │
│                                                                  │
│   ③ 界面显示数据       ↔      Compositor & Painter              │
│      "只描述界面长什么样"        "只负责把计算结果画到屏幕"        │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

**关键洞察**：浏览器花了几十年的工程演进（从 Netscape 到 Chromium），才打磨出这条 `数据获取 → 计算处理 → 像素输出` 的管线。前端代码的三层分离，**不是在发明什么新东西，而是在应用层复现浏览器底层已经验证过的架构**。

### 3.3 浏览器架构对前端代码的深层隐喻

#### 隐喻一：数据流的单向性

```
浏览器底层：  Network → Parser → Layout → Paint → Composite → Screen
                  ↓          ↓          ↓         ↓          ↓
              不可逆，不可逆，不可逆，不可逆，不可逆

前端代码：    API 响应 → 原始数据 → 算法转换 → 显示数据 → 框架渲染 → DOM
                  ↓          ↓          ↓         ↓          ↓
              单向流动，每一层只依赖上一层的输出
```

浏览器内部的数据流是**严格单向**的——网络栈不会等绘制完再决定怎么解析 HTML。同样，前端代码也应该是单向的：接口数据进来，经过算法，产出显示数据，交给框架渲染。**反向依赖（在渲染层直接操作原始数据、或在算法层直接操作 DOM）就像让浏览器的 Compositor 去发 HTTP 请求一样荒谬。**

#### 隐喻二：层间接口的最小化

浏览器各层之间的接口极其精简：

| 层间边界          | 传递的数据                | 说明                          |
| ----------------- | ------------------------- | ----------------------------- |
| Network → Parser  | HTML/CSS 字节流           | 只有字节，没有业务语义        |
| Parser → Layout   | DOM Tree + CSSOM          | 只有结构化节点，没有像素信息  |
| Layout → Paint    | Render Tree（含几何信息） | 只有位置和样式，没有绘制指令  |
| Paint → Composite | 图层 + 绘制指令           | 只有光栅化信息，没有 DOM 引用 |

**每一层只向下一层传递"下一层需要的最少信息"，绝不透传自己的内部细节。**

前端代码的三层分离也应该如此：

```
接口原始数据 → 算法层：只传算法需要的字段，不是整个 response
算法层 → 显示数据：只传 UI 需要的结构，不是整个计算中间态
显示数据 → 框架：只传模板绑定的变量，不是整个业务对象
```

#### 隐喻三：纯函数的哲学

浏览器的 Rendering Engine 在核心环节上都是**纯函数**：

- `parse(html) → DOM Tree`：同样的 HTML 永远解析出同样的 DOM
- `layout(DOM, CSSOM) → Render Tree`：同样的样式永远算出同样的布局
- `paint(Render Tree) → 绘制指令`：同样的 Render Tree 永远产出同样的指令

这就是为什么浏览器可以缓存、可以增量更新、可以做 requestAnimationFrame 批处理——因为核心环节是确定性的。

前端代码的算法层也应该是纯函数：

```javascript
// ✅ 纯函数：同样的输入永远产出同样的输出
function buildTableData(rawApiData, filters) {
  return rawApiData
    .filter((row) => matchesFilters(row, filters))
    .map((row) => transformRow(row))
    .sort(compareFn)
}

// 可以缓存、可以测试、可以复用、可以并行
```

#### 隐喻四：关注点分离带来的性能优化空间

浏览器之所以能做增量渲染（Streaming）、异步合成（Async Compositing）、GPU 加速，**前提就是层与层之间足够解耦**——每一层可以独立优化，不影响其他层。

前端代码同理：

| 分离带来的好处 | 说明                                                |
| -------------- | --------------------------------------------------- |
| **可缓存**     | 算法层是纯函数，结果可以 memoize                    |
| **可测试**     | 算法层不依赖 DOM，可以在 Node.js 里跑单测           |
| **可复用**     | 同一套算法，可以驱动不同的 UI（PC / Mobile / 报表） |
| **可优化**     | 算法层可以用 Web Worker 跑，不阻塞渲染              |
| **可调试**     | 每一层的数据都可以独立 inspect                      |

## 四、框架演进视角：从对抗到回归

### 4.1 历史回顾

```
jQuery 时代
  └─ 数据和 DOM 完全耦合：$('#list').html(data.map(...))
  └─ 没有分离，全靠纪律

Angular 1.x 时代
  └─ $scope 把原始数据、计算逻辑、视图模型混在一起
  └─ 脏检查机制试图用框架能力弥补架构缺陷

React 时代
  └─ 提出 "UI = f(state)"，state 开始区分 props / state
  └─ 但 hooks 中仍然常见数据获取 + 转换 + 渲染混写

Vue 3 时代
  └─ Composition API 天然支持三层分离
  └─ composable 可以承载算法层，ref/reactive 承载显示数据层
  └─ 但框架并不强制——不分离也能跑，只是代码质量不同
```

### 4.2 框架的局限

**没有任何前端框架能替你完成这三层分离。** 框架能做的只是：

- 提供响应式系统，让"显示数据 → DOM"的同步自动化
- 提供组件化机制，让显示数据的组织更清晰
- 提供生命周期钩子，让你知道什么时候该拿数据、什么时候该渲染

但 **接口原始数据怎么存、算法逻辑放哪里、显示数据怎么构造**——这些全是开发者的架构决策，框架管不了。

### 4.3 回归朴素

真正优秀的代码，往往不是"用了多高级的框架特性"，而是**把最朴素的分离做到了极致**：

```
✅ 接口原始数据：存在独立的数据层（store / repository），组件不直接持有
✅ 算法逻辑：写成纯函数，放在独立的模块（utils / transforms），不 import 框架
✅ 界面显示数据：由组件自己管理（ref / reactive），结构完全匹配模板需要
```

## 五、实践指南：如何落地

### 5.1 目录结构建议

```
src/
├── api/                    # 接口原始数据层
│   ├── user-api.js         # 只负责发请求、返回原始响应
│   └── order-api.js
│
├── transforms/             # 算法层
│   ├── user-transform.js   # 纯函数：原始数据 → 显示数据
│   └── order-transform.js
│
├── components/             # 界面显示层
│   ├── UserList.vue        # 只关心显示数据和交互
│   └── OrderTable.vue
│
└── composables/            # 胶水层：串联三者
    └── useUserList.js      # 调 API → 调 transform → 赋值给 ref
```

### 5.2 三层之间的"防火墙"规则

| 规则                 | 说明                                                    |
| -------------------- | ------------------------------------------------------- |
| 算法层不 import 框架 | `transform.js` 里不应该出现 `import { ref } from 'vue'` |
| 组件层不直接调 API   | 组件通过 composable 间接获取，不直接 `fetch`            |
| 原始数据不进模板     | 模板中不应该出现 `item.raw_api_field_name`              |
| 算法层不操作 DOM     | 算法层不知道 `document` 的存在                          |

### 5.3 检验标准

问自己三个问题：

1. **如果把后端接口换掉（比如从 REST 换成 GraphQL），需要改几个文件？**
   - 只改 `api/` 目录 → ✅ 分离良好
   - 要改组件 → ❌ 原始数据渗透到了视图层

2. **如果要把同一份数据换一种 UI 展示（比如列表变卡片），需要改几个文件？**
   - 只改组件 → ✅ 分离良好
   - 要改算法逻辑 → ❌ 算法和显示耦合

3. **算法逻辑能不能直接在 Node.js 里跑？**
   - 能 → ✅ 纯函数，不依赖框架
   - 不能 → ❌ 算法层被框架或 DOM 污染

## 六、总结

```
┌─────────────────────────────────────────────────────────────────┐
│                                                                  │
│   浏览器的设计：                                                  │
│   Network → Parse → Layout → Paint → Composite → Screen         │
│                                                                  │
│   前端代码的设计：                                                │
│   API → Raw Data → Transform → View Model → Framework → DOM     │
│                                                                  │
│   两者同构，因为本质相同：                                        │
│   "获取数据 → 计算处理 → 输出呈现"                                │
│                                                                  │
│   这不是设计模式，不是最佳实践，不是规范约束。                     │
│   这是前端编程的终极朴素思想——                                   │
│   与浏览器同构，与计算本质一致。                                  │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

**框架会过时，思想不会。** 当你不确定代码该怎么组织时，回到浏览器本身看看——它已经用几十年的工程演进告诉你答案了。
