# React 底层万用公式：Fiber 架构 × 并发调度 × 数据视图同步

> React 18 之后的一切设计——并发模式、Suspense、Transitions、Server Components——都建立在同一个底层架构之上：**Fiber 架构 × 并发调度 × 数据视图同步**。理解这个公式，就理解了 React 为什么需要 `memo`、为什么 `useEffect` 是异步的、为什么 `startTransition` 能提升流畅度、为什么 React 的渲染模型与 Vue 根本不同。本文从 React 的底层架构出发，推导出这个万用公式。

---

## 一、Fiber 架构：React 的渲染引擎

### 1.1 为什么需要 Fiber

React 15 及之前的渲染器（Stack Reconciler）有一个致命缺陷：**递归不可中断**。

```
┌─────────────────────────────────────────────────────────────────┐
│                  Stack Reconciler（React 15）的致命缺陷            │
│                                                                  │
│  setState → 递归遍历整棵组件树 → 生成 VNode → Diff → Patch      │
│                                                                  │
│  问题：递归一旦开始，就不能中断                                   │
│                                                                  │
│  组件树：                                                         │
│        App                                                       │
│       / | \                                                      │
│     Nav  Main  Sidebar                                           │
│         / | \                                                    │
│      Header List Footer                                          │
│            / | \                                                 │
│         Item Item Item ... (1000 个)                             │
│                                                                  │
│  如果 setState 触发了 1000 个 Item 的 Diff：                     │
│  → 递归必须一口气跑完 1000 个节点                                 │
│  → 整个过程占用主线程，无法响应用户输入                           │
│  → 如果耗时 200ms → 用户感知到明显卡顿                           │
│                                                                  │
│  根本原因：JS 的执行是同步的，递归调用栈不可中断                  │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

**Fiber 的核心创新**：把"不可中断的递归"变成"可中断的链表遍历"。

### 1.2 Fiber Node 的数据结构

Fiber 的本质是一个 JS 对象，它用链表结构替代了树结构的递归遍历：

```javascript
// Fiber Node 的核心结构（简化版）
{
  // ── 节点身份 ──
  type: 'div',           // 组件类型或 DOM 标签
  key: 'item-1',         // 列表中的唯一标识

  // ── 链表指针（替代树的 children 数组）──
  child: fiberNode,      // 第一个子节点
  sibling: fiberNode,    // 下一个兄弟节点
  return: fiberNode,     // 父节点

  // ── 状态 ──
  memoizedState: hook,   // Hooks 链表（函数组件）
  memoizedProps: {},     // 上次渲染的 props
  pendingProps: {},      // 新的 props

  // ── 副作用 ──
  flags: 'Placement',    // 副作用标记（新增/更新/删除）
  updateQueue: {},       // 待处理的更新

  // ── 调度 ──
  lanes: 1,              // 优先级车道
  alternate: fiberNode,  // 指向另一棵树中对应的节点
}
```

```
┌─────────────────────────────────────────────────────────────────┐
│                  Fiber 链表结构                                    │
│                                                                  │
│  传统树结构（递归遍历）：          Fiber 链表结构（循环遍历）：     │
│                                                                  │
│        App                         App                           │
│       / | \                        |                             │
│     A   B   C                     Nav ─→ Main ─→ Sidebar        │
│        |                           |        |                    │
│       List                       Header   List                  │
│      / | \                               |                      │
│    I1  I2  I3                          I1 ─→ I2 ─→ I3          │
│                                                                  │
│  遍历方式：递归调用栈               遍历方式：while 循环          │
│  可中断？❌ 不可中断                可中断？✅ 每个节点后可暂停   │
│                                                                  │
│  遍历顺序（深度优先）：             遍历顺序（相同，但可暂停）：   │
│  App → A → B → List → I1 → I2     App → Nav → Header           │
│  → I3 → C（一口气跑完）            → [可在此暂停！]              │
│                                   → Main → List → I1            │
│                                   → [可在此暂停！]              │
│                                   → ...                         │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

### 1.3 双缓冲机制：current 树与 workInProgress 树

Fiber 架构维护两棵完整的 Fiber 树：

```
┌─────────────────────────────────────────────────────────────────┐
│                  双缓冲（Double Buffering）                       │
│                                                                  │
│  current 树（当前显示在屏幕上的）                                 │
│  ┌─────────────────────────────────┐                             │
│  │  App (current)                  │ ← 用户正在看到的             │
│  │  └→ Nav → Main → Sidebar       │                             │
│  └─────────────────────────────────┘                             │
│                                                                  │
│  workInProgress 树（在内存中构建的）                              │
│  ┌─────────────────────────────────┐                             │
│  │  App (workInProgress)           │ ← 正在计算中的               │
│  │  └→ Nav → Main → Sidebar       │                             │
│  │      (新状态)                    │                             │
│  └─────────────────────────────────┘                             │
│                                                                  │
│  渲染流程：                                                       │
│  ① 在 workInProgress 树上执行所有计算（Diff、创建 DOM 节点）      │
│  ② 计算全部完成后，一次性将 workInProgress 切换为 current         │
│  ③ 用户看到更新后的界面                                           │
│                                                                  │
│  与浏览器渲染管线的类比：                                         │
│  workInProgress = 后缓冲（Back Buffer）→ 在内存中绘制下一帧      │
│  current = 前缓冲（Front Buffer）→ 正在显示给用户                 │
│  切换 = Page Flip → 一帧完成，无撕裂                              │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

## 二、并发调度：Fiber 带来的革命

### 2.1 可中断渲染的实现原理

Fiber 链表结构让 React 可以在任意两个 Fiber Node 之间暂停：

```
┌─────────────────────────────────────────────────────────────────┐
│                  可中断渲染的时间线                                 │
│                                                                  │
│  主线程时间轴 →                                                   │
│                                                                  │
│  ┌─────────┐┌──────┐┌─────────┐┌──────┐┌─────────┐┌──────┐    │
│  │ React   ││ 渲染 ││ React   ││ 渲染 ││ React   ││ 渲染 │    │
│  │ 工作单元││ 帧   ││ 工作单元││ 帧   ││ 工作单元││ 帧   │    │
│  │ (几个   ││      ││ (几个   ││      ││ (完成!) ││      │    │
│  │  Fiber) ││      ││  Fiber) ││      ││         ││      │    │
│  └─────────┘└──────┘└─────────┘└──────┘└─────────┘└──────┘    │
│                                                                  │
│  每个"工作单元"处理几个 Fiber Node 后：                           │
│  → 检查是否还有剩余时间（shouldYield()）                         │
│  → 有时间 → 继续处理下一批 Fiber                                 │
│  → 没时间 → 暂停 React 工作，让出主线程给渲染/用户事件           │
│                                                                  │
│  这就是 React 18 并发模式的核心：                                 │
│  渲染不再是"一口气跑完"，而是"分片执行，随时可暂停"              │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

### 2.2 调度器（Scheduler）的优先级模型

React 的调度器借鉴了操作系统的线程优先级模型：

```
┌─────────────────────────────────────────────────────────────────┐
│                  React 调度器的优先级层级                          │
│                                                                  │
│  优先级（从高到低）：                                              │
│                                                                  │
│  ┌──────────────────────────────────────────────────────┐        │
│  │  ImmediatePriority（立即优先级）                      │        │
│  │  • 同步执行，不可延迟                                  │        │
│  │  • 场景：用户输入的即时反馈（如 input 光标位置）       │        │
│  └──────────────────────────────────────────────────────┘        │
│                          ↓                                       │
│  ┌──────────────────────────────────────────────────────┐        │
│  │  UserBlockingPriority（用户阻塞优先级）               │        │
│  │  • 应在下一帧（~16ms）内完成                           │        │
│  │  • 场景：点击按钮、拖拽等用户直接交互                  │        │
│  └──────────────────────────────────────────────────────┘        │
│                          ↓                                       │
│  ┌──────────────────────────────────────────────────────┐        │
│  │  NormalPriority（普通优先级）                          │        │
│  │  • 默认优先级                                          │        │
│  │  • 场景：大多数 setState 触发的更新                    │        │
│  └──────────────────────────────────────────────────────┘        │
│                          ↓                                       │
│  ┌──────────────────────────────────────────────────────┐        │
│  │  LowPriority（低优先级）                               │        │
│  │  • 可以延迟执行                                        │        │
│  │  • 场景：数据预取、非关键 UI 更新                      │        │
│  └──────────────────────────────────────────────────────┘        │
│                          ↓                                       │
│  ┌──────────────────────────────────────────────────────┐        │
│  │  IdlePriority（空闲优先级）                            │        │
│  │  • 永远不应该阻塞渲染                                  │        │
│  │  • 场景：Profiler、DevTools 更新                      │        │
│  └──────────────────────────────────────────────────────┘        │
│                                                                  │
│  调度规则：高优先级任务可以中断低优先级任务                       │
│  用户输入（UserBlocking）> 普通渲染（Normal）> 数据预取（Low）   │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

### 2.3 startTransition 与 useDeferredValue 的底层机制

```
┌─────────────────────────────────────────────────────────────────┐
│                  startTransition 的底层机制                       │
│                                                                  │
│  没有 startTransition：                                           │
│  ┌──────────────────────────────────────────────────────┐        │
│  │ setState(query) → NormalPriority 渲染 → 不可中断     │        │
│  │ → 如果渲染耗时 300ms → 主线程被阻塞 300ms             │        │
│  │ → 用户输入被延迟响应 → 卡顿                           │        │
│  └──────────────────────────────────────────────────────┘        │
│                                                                  │
│  使用 startTransition：                                           │
│  ┌──────────────────────────────────────────────────────┐        │
│  │ setState(input) → UserBlockingPriority → 立即渲染    │        │
│  │ startTransition(() => {                              │        │
│  │   setState(query) → LowPriority → 可被中断           │        │
│  │ })                                                    │        │
│  │                                                       │        │
│  │ 时间线：                                               │        │
│  │ [input 渲染 5ms] [用户输入] [query 渲染 50ms]         │        │
│  │ [input 渲染 5ms] [用户输入] [query 渲染被中断!]       │        │
│  │ [input 渲染 5ms] [用户输入] [query 继续渲染...]       │        │
│  │                                                       │        │
│  │ → 用户输入始终被即时响应                                │        │
│  │ → query 渲染在后台分片执行                              │        │
│  │ → 最终结果一致，但过程流畅                              │        │
│  └──────────────────────────────────────────────────────┘        │
│                                                                  │
│  本质：startTransition 把更新标记为"可中断的低优先级"            │
│  调度器在发现更高优先级任务时，会暂停当前渲染去处理它            │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

## 三、数据视图同步：React 的同步模型

### 3.1 React 的同步模型：显式触发 + 批量合并

```
┌─────────────────────────────────────────────────────────────────┐
│                  React 数据视图同步的完整链路                      │
│                                                                  │
│  ① 状态变更触发                                                   │
│     setState(newState)                                            │
│     → 创建 Update 对象，挂到 Fiber 的 updateQueue 上             │
│     → 调度器根据优先级决定何时开始渲染                            │
│                                                                  │
│  ② 调度器启动渲染                                                 │
│     Scheduler 从任务队列取出渲染任务                              │
│     → 开始遍历 Fiber 链表                                         │
│                                                                  │
│  ③ Render 阶段（可中断，纯计算，不产生副作用）                    │
│     从根 Fiber 开始遍历每个 Fiber Node：                          │
│     → 执行组件函数（re-render）                                   │
│     → 生成新的 VNode（React Element）                             │
│     → 与旧 VNode 做 Diff（Reconciliation）                       │
│     → 标记需要更新的 Fiber（flags）                               │
│     → 可随时暂停，保存进度到 workInProgress 树                    │
│                                                                  │
│  ④ Commit 阶段（不可中断，产生 DOM 副作用）                       │
│     遍历所有带 flags 的 Fiber：                                   │
│     → Before Mutation：执行 useLayoutEffect 的销毁函数            │
│     → Mutation：执行真实 DOM 操作（insert/update/delete）         │
│     → Layout：执行 useLayoutEffect 的回调、ref 赋值              │
│     → 切换 current 和 workInProgress                              │
│     → 执行 useEffect 的回调（异步，在下一次宏任务中）            │
│                                                                  │
│  ⑤ 浏览器渲染                                                     │
│     DOM 变更 → 浏览器渲染管线 → 像素更新到屏幕                   │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

### 3.2 Render 阶段 vs Commit 阶段的关键区别

```
┌─────────────────────────────────────────────────────────────────┐
│                  Render 阶段 vs Commit 阶段                       │
│                                                                  │
│              Render 阶段              Commit 阶段                 │
│  ─────────    ──────────────         ──────────────              │
│  可中断？      ✅ 可中断              ❌ 不可中断                  │
│  副作用？      ❌ 纯计算              ✅ DOM 操作 + 副作用         │
│  组件函数？    ✅ 可能多次执行        ❌ 不执行                    │
│  useEffect？   ❌ 不执行              ✅ 异步执行（commit 后）     │
│  useLayout？   ❌ 不执行              ✅ 同步执行（commit 中）     │
│                                                                  │
│  关键推论：                                                        │
│  • Render 阶段可能被中断并重新开始 → 组件函数可能执行多次         │
│  • 所以 Render 阶段必须是"纯"的，不能有副作用                    │
│  • 这就是为什么 useEffect 中的代码在 Render 之后执行             │
│  • 这也是为什么 setState 在 Render 阶段调用会报警告              │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

### 3.3 useEffect 的同步时序：为什么它是"异步的"

```
┌─────────────────────────────────────────────────────────────────┐
│                  useEffect 在事件循环中的精确位置                   │
│                                                                  │
│  时间轴 →                                                        │
│                                                                  │
│  ┌──────────────┐                                               │
│  │ 宏任务：      │                                               │
│  │ 用户点击      │                                               │
│  │ → setState() │  ← 创建 Update，推入调度队列                   │
│  └──────────────┘                                               │
│           ↓                                                      │
│  ┌──────────────┐                                               │
│  │ React Render │  ← Fiber 遍历（可中断）                        │
│  │ 阶段          │  → 组件函数重新执行                           │
│  │              │  → Diff 计算                                   │
│  └──────────────┘                                               │
│           ↓                                                      │
│  ┌──────────────┐                                               │
│  │ React Commit │  ← 不可中断                                    │
│  │ 阶段          │  → DOM 操作                                   │
│  │              │  → useLayoutEffect 同步执行                    │
│  └──────────────┘                                               │
│           ↓                                                      │
│  ┌──────────────┐                                               │
│  │ 浏览器渲染    │  ← Style → Layout → Paint                    │
│  └──────────────┘                                               │
│           ↓                                                      │
│  ┌──────────────┐                                               │
│  │ 微任务/宏任务│  ← useEffect 回调在此执行                     │
│  │ useEffect    │  → 异步执行，不阻塞渲染                       │
│  │ 回调执行      │  → 如果 effect 中 setState → 新的更新周期    │
│  └──────────────┘                                               │
│                                                                  │
│  关键：useEffect 在"浏览器渲染之后"才执行                       │
│  → 用户先看到 UI 更新，然后 effect 才运行                        │
│  → 如果 effect 中又 setState → 用户可能看到"闪烁"               │
│  → 如果需要"同步"效果（不闪烁），用 useLayoutEffect             │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

## 四、万用公式：React 版本的三柱合一

### 4.1 公式

```
┌─────────────────────────────────────────────────────────────────┐
│                                                                  │
│   React 的底层万用公式：                                         │
│                                                                  │
│   Fiber 架构 × 并发调度 × 数据视图同步                           │
│                                                                  │
│   Fiber 架构：                                                    │
│   把不可中断的递归变成可中断的链表遍历                            │
│   → 双缓冲（current + workInProgress）                          │
│   → 这是所有后续优化的物理基础                                    │
│                                                                  │
│   并发调度：                                                      │
│   基于优先级的任务调度，高优先级可中断低优先级                    │
│   → startTransition / useDeferredValue                          │
│   → 让开发者控制"哪些更新可以等"                                 │
│                                                                  │
│   数据视图同步：                                                  │
│   setState → Render（可中断，纯计算）→ Commit（不可中断，DOM）   │
│   → Render 阶段必须纯，副作用只能在 Commit 后                   │
│                                                                  │
│   ════════════════════════════════════════════════════════════    │
│                                                                  │
│   与 Vue 万用公式的对比：                                         │
│                                                                  │
│   Vue：    渲染原理 × 事件调度 × 数据视图同步                    │
│   React：  Fiber 架构 × 并发调度 × 数据视图同步                  │
│                                                                  │
│   相同点：最终都是"数据变化 → 计算差异 → DOM Patch → 渲染"      │
│   差异点：                                                        │
│   • Vue 用 Proxy 依赖图实现"精确通知"                           │
│   • React 用 Fiber 链表实现"可中断渲染"                          │
│   • Vue 的调度在微任务层面（批量合并）                           │
│   • React 的调度在 Scheduler 层面（优先级队列）                  │
│   • Vue 默认精确更新，React 默认全量重跑                        │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

### 4.2 公式推论：React 设计决策的底层解释

```
┌─────────────────────────────────────────────────────────────────┐
│                  万用公式解释 React 的核心设计决策                 │
│                                                                  │
│  为什么 React 需要 React.memo？                                  │
│  → Fiber 遍历会重新执行每个子组件函数                            │
│  → memo 通过浅比较 props 跳过不必要的函数执行                    │
│  → 本质：在 Render 阶段做"剪枝"，减少 Fiber 遍历的工作量        │
│                                                                  │
│  为什么 useEffect 是异步的？                                     │
│  → Commit 阶段完成后，浏览器先渲染一帧                           │
│  → useEffect 在下一帧的宏任务/微任务中执行                       │
│  → 设计意图：不阻塞渲染，让界面先更新                            │
│                                                                  │
│  为什么 Render 阶段不能有副作用？                                 │
│  → Render 阶段可能被中断并重新开始                               │
│  → 组件函数可能执行多次（Strict Mode 下故意执行两次）            │
│  → 如果有副作用（如发请求、改 DOM）→ 会重复执行 → 数据错乱     │
│                                                                  │
│  为什么需要 key？                                                 │
│  → Fiber Diff 算法依赖 key 来识别"哪个节点是哪个"               │
│  → 没有 key → 只能按位置对比 → 列表重排时大量误判              │
│  → 有 key → 精确定位 → Diff 效率从 O(n²) 降到 O(n)             │
│                                                                  │
│  为什么 React 18 引入并发特性？                                   │
│  → Fiber 架构让渲染可中断                                        │
│  → 调度器让中断后的恢复有优先级                                  │
│  → startTransition 让开发者声明"这个更新不急"                   │
│  → 本质：把"是否中断"的决策权从框架扩展到开发者                 │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

### 4.3 跨框架对比：三大框架的底层公式

```
┌─────────────────────────────────────────────────────────────────┐
│                  三大框架的底层公式对比                             │
│                                                                  │
│  Vue 3：                                                         │
│  Proxy 依赖图 × 微任务批量 × 精确响应式更新                      │
│  → 默认精确：只有依赖变更的组件才更新                            │
│  → 开发者责任：避免过度响应（shallowRef）                        │
│  → 渲染粒度：组件级                                              │
│                                                                  │
│  React 18：                                                      │
│  Fiber 链表 × 优先级调度 × 全量 Re-render + Diff                │
│  → 默认全量：父组件更新 → 所有子组件函数重跑                    │
│  → 开发者责任：主动阻断传播（memo / useMemo）                    │
│  → 渲染粒度：组件级（但可中断、可恢复）                          │
│                                                                  │
│  Solid.js：                                                      │
│  Signals × 细粒度依赖图 × 直接 DOM 操作                          │
│  → 默认精确到 DOM 节点：不经过 Virtual DOM                      │
│  → 开发者责任：正确使用 Signals 原语                             │
│  → 渲染粒度：DOM 节点级（最精细）                                │
│                                                                  │
│  共同公式：数据变化 → 依赖分析 → 差异计算 → DOM 更新 → 渲染    │
│  差异只在"依赖分析"和"差异计算"的实现策略                       │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

## 五、用公式诊断 React 性能问题

### 5.1 诊断决策树

```
┌─────────────────────────────────────────────────────────────────┐
│                  React 性能问题诊断决策树                          │
│                                                                  │
│  用户报告卡顿                                                      │
│       ↓                                                          │
│  用 React DevTools Profiler 录制                                 │
│       ↓                                                          │
│  观察火焰图：                                                      │
│       │                                                          │
│       ├─ 大量组件被标记为"重新渲染"但 props 没变                 │
│       │   → 问题在"Render 阶段"：缺少 memo 阻断                  │
│       │   → 解法：React.memo + useMemo + useCallback             │
│       │                                                          │
│       ├─ 少量组件但单个组件渲染耗时很长                          │
│       │   → 问题在"Render 阶段"：组件内计算太重                  │
│       │   → 解法：useMemo 缓存 / 虚拟滚动 / 拆分组件             │
│       │                                                          │
│       ├─ 用户交互时界面冻结                                       │
│       │   → 问题在"调度"：渲染任务优先级太高，阻塞用户事件      │
│       │   → 解法：startTransition 降低优先级                      │
│       │                                                          │
│       ├─ useEffect 中 setState 导致循环渲染                      │
│       │   → 问题在"数据视图同步"：effect 链式触发               │
│       │   → 解法：改用 useMemo 同步计算链                        │
│       │                                                          │
│       └─ 大列表渲染卡顿                                           │
│           → 问题在"Commit 阶段"：DOM 操作太多                   │
│           → 解法：虚拟滚动（react-window）                       │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

### 5.2 性能优化与公式环节的映射

```
┌─────────────────────────────────────────────────────────────────┐
│                  优化手段 → 公式环节的映射                         │
│                                                                  │
│  优化手段                  作用于公式的哪一环                     │
│  ──────────────           ──────────────────────                 │
│  React.memo               Render 阶段：跳过不必要的函数执行      │
│  useMemo / useCallback    Render 阶段：稳定引用，辅助 memo 生效  │
│  startTransition          调度层：降低更新优先级，允许中断        │
│  useDeferredValue         调度层：延迟某个值的更新               │
│  虚拟滚动                 Commit 阶段：减少 DOM 操作数量         │
│  React.lazy + Suspense    调度层：按需加载组件代码                │
│  组件拆分                 Render 阶段：减少 Fiber 遍历范围       │
│  状态下沉                 Render 阶段：缩小 state 变更的影响范围 │
│  useTransition            调度层：区分高/低优先级更新             │
│                                                                  │
│  对比 Vue 的优化映射：                                            │
│  Vue 的优化主要在"依赖通知"环节（shallowRef 切断追踪）           │
│  React 的优化主要在"Render 阶段"（memo 阻断遍历）               │
│  因为 Vue 默认精确通知，React 默认全量遍历                      │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

## 六、总结

```
┌─────────────────────────────────────────────────────────────────┐
│                                                                  │
│   React 的底层万用公式：                                         │
│                                                                  │
│   Fiber 架构 × 并发调度 × 数据视图同步                           │
│                                                                  │
│   Fiber 架构：                                                    │
│   把不可中断的递归变成可中断的链表遍历                            │
│   → 双缓冲机制保障渲染一致性                                     │
│   → 这是 React 18 并发的物理基础                                 │
│                                                                  │
│   并发调度：                                                      │
│   基于优先级的可中断渲染                                          │
│   → 高优先级（用户输入）可以打断低优先级（数据更新）             │
│   → startTransition 让开发者参与优先级决策                       │
│                                                                  │
│   数据视图同步：                                                  │
│   Render（可中断，纯计算）→ Commit（不可中断，DOM 操作）         │
│   → Render 阶段必须纯，副作用只能在 Commit 后                   │
│   → useEffect 在浏览器渲染后异步执行                             │
│                                                                  │
│   ════════════════════════════════════════════════════════════    │
│                                                                  │
│   理解这个公式的意义：                                            │
│                                                                  │
│   • 知道为什么需要 memo → Fiber 默认全量遍历                    │
│   • 知道为什么 useEffect 是异步的 → Commit 后才执行             │
│   • 知道为什么 Render 阶段不能副作用 → 可能被执行多次            │
│   • 知道为什么 startTransition 能提升流畅度 → 优先级调度        │
│   • 知道为什么 React 和 Vue 的优化方向相反 → 默认模型不同       │
│                                                                  │
│   公式不同，但目标相同：                                          │
│   用最少的渲染工作量，把正确的像素画到屏幕上                     │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

**Fiber 架构是 React 的分水岭。** React 15 之前，它只是一个"用 JS 模拟 DOM"的库；React 18 之后，它是一个拥有并发调度能力的渲染引擎。理解 Fiber × 并发调度 × 数据视图同步这个公式，就理解了 React 从 API 到性能优化的所有设计决策——它不再是"一个需要记忆规则的库"，而是"一个有清晰设计逻辑的系统"。
