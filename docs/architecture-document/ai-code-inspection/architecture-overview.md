# 大型项目 AI 代码检查脚本集合 — 架构概述

> 传统 Lint 工具（ESLint、Prettier、SonarQube）解决了"语法和格式"层面的代码质量。但当项目规模增长到数百个模块、数十位开发者时，真正影响代码质量的检查——架构违规、安全隐患、业务逻辑缺陷、可维护性退化——往往超出了确定性规则的能力范围。AI 代码检查，正是为了补上这一层。

---

## 一、定位：AI 检查与传统 Lint 的互补关系

### 1.1 能力边界对比

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                    代码检查能力谱系                                           │
│                                                                             │
│   确定性规则（传统 Lint）                    概率性判断（AI 检查）            │
│   ┌─────────────────────────────┐            ┌─────────────────────────────┐│
│   │  ESLint / Prettier          │            │  AI 代码检查                 ││
│   │  • 缩进/分号/引号风格        │            │  • 架构分层是否被违反        ││
│   │  • 未使用变量/导入           │            │  • 函数职责是否过于混杂      ││
│   │  • 类型错误（TypeScript）    │            │  • 命名是否准确表达意图      ││
│   │  • 已知安全模式（XSS/注入）  │            │  • 错误处理是否充分          ││
│   │  • 代码格式统一              │            │  • 是否存在潜在的性能陷阱    ││
│   │                             │            │  • 注释与代码是否一致        ││
│   │  特征：速度快、零误报、      │            │  • 业务规则是否被正确实现    ││
│   │        规则明确、无法理解语义 │            │                             ││
│   └─────────────────────────────┘            │  特征：理解语义、灵活判断、  ││
│                                              │        有误报、成本较高      ││
│                                              └─────────────────────────────┘│
│   ◄────────── 语法层 ──────────►◄──────────── 语义层 ────────────────────►  │
│   ◄────────── 确定性 ──────────►◄──────────── 概率性 ────────────────────►  │
│   ◄────────── 零成本 ──────────►◄──────────── 有成本 ────────────────────►  │
└─────────────────────────────────────────────────────────────────────────────┘
```

### 1.2 核心原则

> **AI 检查不替代传统 Lint，而是在 Lint 无法触及的"语义层"提供补充检查能力。**

```
代码提交
  │
  ├── 第一道关卡：传统 Lint（ESLint / Prettier / TypeScript）
  │   └── 秒级反馈，零成本，拦截语法/格式/类型问题
  │
  ├── 第二道关卡：静态分析（SonarQube / CodeQL）
  │   └── 分钟级，中等成本，拦截已知缺陷模式和安全漏洞
  │
  └── 第三道关卡：AI 检查（本文主题）
      └── 分钟级，有 API 成本，拦截语义层/架构层/业务层问题
```

## 二、五层管线架构

AI 代码检查系统的核心是一条**管线（Pipeline）**——代码从一端进入，检查报告从另一端输出。

### 2.1 架构全景

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                    AI 代码检查管线 — 五层架构                                 │
│                                                                             │
│  ① 代码采集层（Code Collector）                                              │
│  ┌─────────────────────────────────────────────────────────────────────┐   │
│  │  输入：Git 仓库                                                      │   │
│  │  • Git diff 提取变更文件                                             │   │
│  │  • 按规则过滤（只检查 *.vue / *.ts / *.js 等目标文件）              │   │
│  │  • 排除策略（node_modules / dist / 生成代码 / 测试文件可选）        │   │
│  │  输出：待检查的文件列表 + 文件内容                                   │   │
│  └─────────────────────────────────────────────────────────────────────┘   │
│                              ↓                                              │
│  ② 上下文组装层（Context Assembler）                                         │
│  ┌─────────────────────────────────────────────────────────────────────┐   │
│  │  输入：文件内容 + 检查规则                                           │   │
│  │  • 注入项目编码规范（作为 AI 的背景知识）                            │   │
│  │  • 注入依赖上下文（import 来源文件的关键信息）                       │   │
│  │  • Token 预算分配（系统指令 / 规范 / 代码 / 输出空间）              │   │
│  │  • 大文件切片（超过上下文窗口的文件分段处理）                        │   │
│  │  输出：组装好的 Prompt 请求                                          │   │
│  └─────────────────────────────────────────────────────────────────────┘   │
│                              ↓                                              │
│  ③ AI 执行层（AI Executor）                                                  │
│  ┌─────────────────────────────────────────────────────────────────────┐   │
│  │  输入：Prompt 请求                                                   │   │
│  │  • 调用 LLM API（GPT / Claude / 本地模型）                          │   │
│  │  • 结构化输出解析（JSON Schema 约束返回格式）                        │   │
│  │  • 重试与降级策略（主模型失败时切换备用模型）                        │   │
│  │  • 并发控制与速率限制                                                │   │
│  │  输出：AI 返回的原始检查结果                                         │   │
│  └─────────────────────────────────────────────────────────────────────┘   │
│                              ↓                                              │
│  ④ 结果处理层（Result Processor）                                            │
│  ┌─────────────────────────────────────────────────────────────────────┐   │
│  │  输入：AI 原始结果                                                   │   │
│  │  • 结果校验（JSON 格式校验、字段完整性检查）                         │   │
│  │  • 去重合并（多条规则命中同一位置时的合并）                          │   │
│  │  • 严重级别映射（error / warning / info）                            │   │
│  │  • 误报抑制（白名单 / 历史忽略列表）                                 │   │
│  │  • 格式化输出（JSON / Markdown / SARIF）                             │   │
│  │  输出：标准化的检查报告                                               │   │
│  └─────────────────────────────────────────────────────────────────────┘   │
│                              ↓                                              │
│  ⑤ 集成层（Integration）                                                    │
│  ┌─────────────────────────────────────────────────────────────────────┐   │
│  │  输入：检查报告                                                       │   │
│  │  • CI/CD：GitHub Actions / GitLab CI 步骤                            │   │
│  │  • PR 评论：自动在 PR 上添加 Review Comment                         │   │
│  │  • 通知：Slack / 飞书 / 邮件                                         │   │
│  │  • 阻断：error 级别问题时阻止合并                                    │   │
│  │  输出：开发者可见的检查反馈                                           │   │
│  └─────────────────────────────────────────────────────────────────────┘   │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

### 2.2 数据流总览

```
Git 仓库
  │
  ↓ [代码采集层]
变更文件列表 + 文件内容
  │
  ↓ [上下文组装层]
组装好的 Prompt（代码 + 规范 + 规则）
  │
  ↓ [AI 执行层]
AI 原始检查结果（JSON）
  │
  ↓ [结果处理层]
标准化检查报告
  │
  ↓ [集成层]
PR 评论 / CI 状态 / 通知消息
```

## 三、大型项目的特殊挑战

### 3.1 挑战与应对策略

| 挑战           | 说明                                      | 应对策略                                      |
| -------------- | ----------------------------------------- | --------------------------------------------- |
| **代码量大**   | 数百个模块、数十万行代码，不可能全量送 AI | diff 精准采集 + 增量检查 + 结果缓存           |
| **多语言混合** | 同一项目可能包含 Vue/TS/Python/Dart       | 统一的检查抽象 + 语言适配器模式               |
| **成本控制**   | LLM API 调用有费用，大量检查成本不可忽视  | 模型分级（简单规则用小模型）+ 缓存 + 批量请求 |
| **检查延迟**   | AI 响应慢（秒级到分钟级），不能阻塞开发   | 异步执行 + PR 评论模式（不阻塞提交）          |
| **误报管理**   | AI 判断有概率性，误报会消耗开发者信任     | 误报抑制列表 + 置信度阈值 + 渐进式引入        |
| **规范一致性** | 不同团队/模块可能有不同的编码规范         | 分层规则体系（全局 → 团队 → 模块级覆盖）      |
| **模型迭代**   | LLM 版本更新可能影响检查结果一致性        | Prompt 版本管理 + 基线测试集 + 模型锁定       |

### 3.2 增量检查 vs 全量扫描

```
┌─────────────────────────────────────────────────────────────────┐
│                                                                  │
│   增量检查（PR 模式）                                             │
│   ├── 触发：PR 创建/更新时                                       │
│   ├── 范围：只检查 diff 涉及的文件和代码行                       │
│   ├── 成本：低（只处理变更部分）                                 │
│   ├── 延迟：低（几分钟内完成）                                   │
│   └── 适用：日常开发，每次提交                                   │
│                                                                  │
│   全量扫描（定时模式）                                            │
│   ├── 触发：每日/每周定时任务                                    │
│   ├── 范围：扫描整个项目的所有目标文件                           │
│   ├── 成本：高（但有缓存机制，未修改文件跳过）                   │
│   ├── 延迟：高（可能需要数十分钟到数小时）                       │
│   └── 适用：质量基线建立、历史债务盘点                           │
│                                                                  │
│   最佳实践：两者结合                                              │
│   ├── 日常开发：增量检查（快速反馈）                              │
│   ├── 每周一次：全量扫描（发现存量问题）                          │
│   └── 版本发布前：全量扫描 + 严格模式（阻断发布）                │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

## 四、技术选型要点

### 4.1 脚本语言选择

| 选项                     | 适用场景   | 说明                                      |
| ------------------------ | ---------- | ----------------------------------------- |
| **Node.js / TypeScript** | 前端项目   | 与项目技术栈一致，方便解析 JS/TS/Vue 代码 |
| **Python**               | 多语言项目 | 丰富的 NLP/文本处理库，AI SDK 生态更成熟  |
| **Shell + 调用 CLI**     | 简单场景   | 快速原型，但复杂逻辑难以维护              |

### 4.2 LLM 选型考量

| 维度           | 考量点                                                             |
| -------------- | ------------------------------------------------------------------ |
| **上下文窗口** | 代码检查需要较大的上下文（代码 + 规范 + 输出空间），至少 8K tokens |
| **结构化输出** | 必须支持 JSON Schema 约束的输出格式，否则解析成本极高              |
| **延迟**       | 单次检查应在 30 秒内完成，否则影响 CI 效率                         |
| **成本**       | 按 token 计费，需要评估月均检查量下的费用                          |
| **一致性**     | 同一输入应产出稳定的结果，避免"今天说有问题明天又说没有"           |
| **可私有化**   | 代码不能外泄的场景需要考虑本地部署模型（Ollama / vLLM）            |

### 4.3 输出格式标准

```json
// AI 检查结果的标准化输出格式
{
  "ruleId": "arch-layer-violation",
  "severity": "error",
  "file": "src/components/UserList.vue",
  "line": 42,
  "column": 5,
  "message": "组件直接调用了 API 层函数 fetchUsers()，违反了分层架构规范。应通过 composable 间接调用。",
  "suggestion": "将 fetchUsers() 调用移至 composable/useUserList.js 中，组件只消费 composable 返回的响应式数据。",
  "confidence": 0.92,
  "model": "gpt-4o",
  "promptVersion": "1.2.0"
}
```

## 五、项目目录结构建议

```
ai-code-inspection/
├── scripts/                        # 检查脚本
│   ├── runner.js                   # 主运行器（入口）
│   ├── collector.js                # 代码采集层
│   ├── assembler.js                # 上下文组装层
│   ├── executor.js                 # AI 执行层
│   ├── processor.js                # 结果处理层
│   └── reporter.js                 # 报告生成器
│
├── rules/                          # 检查规则
│   ├── code-quality.js             # 代码质量规则
│   ├── security.js                 # 安全检查规则
│   ├── architecture.js             # 架构合规规则
│   ├── performance.js              # 性能检查规则
│   └── _template.js                # 自定义规则模板
│
├── prompts/                        # Prompt 模板
│   ├── code-quality.md             # 代码质量检查 Prompt
│   ├── security.md                 # 安全检查 Prompt
│   ├── architecture.md             # 架构检查 Prompt
│   └── _template.md                # Prompt 模板
│
├── config/                         # 配置
│   ├── default.json                # 默认配置
│   └── project-template.json       # 项目级配置模板
│
└── tests/                          # 测试
    ├── fixtures/                   # 测试用例代码片段
    └── rules.test.js               # 规则测试
```
